# 常见架构与设计反模式

## 架构反模式

### 1. 大泥球（Big Ball of Mud）
**特征**：没有清晰结构，代码随意堆积
**后果**：难以维护、难以测试、难以扩展
**解决**：重构为分层架构，明确模块边界

### 2.  lava 流（Lava Flow）
**特征**：遗留的死代码无人敢动
**后果**：代码库膨胀，新功能开发受阻
**解决**：渐进式重构，编写测试，删除无用代码

### 3. 金锤（Golden Hammer）
**特征**：对所有问题使用同一种解决方案
**后果**：不适用场景下效率低下
**解决**：根据问题选择合适的工具

### 4. 皇帝新衣（Emperor's New Clothes）
**特征**：使用过度复杂的技术解决简单问题
**后果**：不必要的复杂度，维护困难
**解决**：保持简单，YAGNI 原则

### 5. 烟囱系统（Stovepipe System）
**特征**：系统间缺乏集成，各自为政
**后果**：数据孤岛，重复开发
**解决**：建立共享服务，统一数据模型

## 设计反模式

### 1. 上帝类（God Class）
**特征**：一个类做太多事情
**后果**：难以测试、难以维护
**解决**：拆分为多个职责单一的类

### 2. 贫血模型（Anemic Domain Model）
**特征**：模型只有数据没有行为
**后果**：业务逻辑分散，难以维护
**解决**：将行为封装到领域模型中

### 3. 循环依赖（Circular Dependency）
**特征**：模块间相互依赖
**后果**：无法独立测试、部署
**解决**：引入接口、依赖注入、事件驱动

### 4. 紧耦合（Tight Coupling）
**特征**：模块间高度依赖
**后果**：修改一处影响多处
**解决**：依赖抽象、松耦合设计

### 5. 过早抽象（Premature Abstraction）
**特征**：为不确定的需求做抽象
**后果**：增加复杂度，灵活性反而降低
**解决**：三次法则，确实需要时再抽象

## 微服务反模式

### 1. 分布式单体（Distributed Monolith）
**特征**：服务间强耦合，必须一起部署
**后果**：失去微服务的优势，增加复杂度
**解决**：理清服务边界，减少同步调用

### 2. 纳米服务（Nanoservices）
**特征**：服务粒度过细
**后果】管理开销大，网络延迟高
**解决**：合理划分服务边界，合并相关服务

### 3. 共享数据库（Shared Database）
**特征**：多个服务直接操作同一数据库
**后果**：数据耦合，难以独立演进
**解决**：每个服务独立数据库，通过 API 交互

### 4. 循环依赖调用
**特征**：服务间循环调用
**后果**：级联故障，难以追踪
**解决**：重构为异步消息或合并服务

## 性能反模式

### 1. N+1 查询
**特征**：循环中逐个查询数据库
**后果**：数据库压力巨大
**解决**：使用 JOIN 或批量查询

### 2. 过度使用同步阻塞
**特征**：大量同步调用外部服务
**后果**：响应时间累积，系统吞吐量低
**解决**：使用异步、缓存、批量处理

### 3. 忽略缓存
**特征**：所有请求直接打到数据库
**后果**：数据库成为瓶颈
**解决**：多级缓存策略

### 4. 资源泄露
**特征**：连接、线程未正确释放
**后果**：系统资源耗尽，服务崩溃
**解决**：使用 try-with-resources，连接池

## 安全反模式

### 1. 硬编码密钥
**特征**：密码、密钥写在代码中
**后果**：泄露风险
**解决**：使用密钥管理服务

### 2. 不安全的数据传输
**特征**：敏感信息明文传输
**后果**：中间人攻击
**解决**：使用 HTTPS，加密传输

### 3. 缺乏输入验证
**特征**：信任所有输入
**后果**：SQL 注入、XSS 等攻击
**解决**：白名单验证、参数化查询

### 4. 过度授权
**特征**：用户权限过大
**后果**：数据泄露、误操作
**解决**：最小权限原则

## 组织反模式

### 1. 康威定律的反面
**特征**：组织结构和系统架构不匹配
**后果**：沟通成本高，效率低下
**解决**：调整团队结构或系统架构

### 2. 英雄主义
**特征**：依赖个别专家解决所有问题
**后果**：单点故障，知识孤岛
**解决**：知识分享，文档化，代码审查

### 3. 忽视技术债务
**特征**：只关注新功能，不重构
**后果**：系统逐渐僵化
**解决**：预留技术债务偿还时间
