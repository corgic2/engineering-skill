# Solution Validator

此 Skill 强制在任何技术方案、架构设计输出前进行自我评估，确保方案质量。评估采用五维量化评分机制，覆盖软件设计、业务逻辑、代码逻辑、代码风格、代码质量，并必须分析边界条件。

## 分工边界

本 Skill 只负责**纯方案层面的评估**，不产出代码，不修改文件。

- 用户说"设计一个系统给我看看" → 触发本 Skill
- 用户说"帮我写代码实现这个功能" → 触发 spec-driven-agent（含 SDD 工作流）
- 用户说"review 这段代码" → 触发 code-review

## 核心原则

**⚠️ 重要：每次输出设计方案、思路或解决方案前，必须先执行自我评估并输出评分！**

## 触发条件

当用户出现以下任一表述时，必须执行本 Skill 的完整评估流程：
- "输出你的方案"
- "给出你的解决方案"
- "设计一个..."
- "帮我设计方案"
- "输出设计思路"
- "提出技术方案"
- 任何要求提供方案、设计、架构、实现思路的请求

## 评估流程

```
理解需求 → 构思方案 → 五维自评 → 边界分析 → 输出评分 → 输出最终方案
```

## 五维评估框架

每个维度满分 10 分，必须给出具体分数及简要理由。

### 1. 软件设计 (Software Design)

评估架构与宏观设计的合理性：
- **架构合理性**：分层/模块化是否清晰，职责分离是否到位
- **扩展性**：是否易于新增功能或适配变化
- **耦合与内聚**：模块间依赖是否合理，高内聚低耦合程度
- **设计模式**：模式运用是否恰当，有无过度设计

> 评分细则（10/7-9/5-6/<5 各档位标准）见 [references/scoring-rubric.md](references/scoring-rubric.md)

### 2. 业务逻辑 (Business Logic)

评估业务规则与流程的正确性和完整性：
- **需求覆盖度**：是否完整覆盖显式需求
- **规则正确性**：业务规则实现是否准确
- **流程一致性**：数据流、状态流转是否符合业务预期
- **异常业务场景**：非正常业务流程是否被处理

> 评分细则见 [references/scoring-rubric.md](references/scoring-rubric.md)

### 3. 代码逻辑 (Code Logic)

评估具体实现层面的逻辑严谨性：
- **算法正确性**：核心算法、计算逻辑是否正确
- **控制流清晰度**：条件分支、循环、递归是否清晰无误
- **边界条件**：空值、越界、极值、空集合等是否处理
- **并发安全**：多线程/异步场景下是否存在竞态条件
- **资源管理**：文件、连接、锁是否正确释放

> 评分细则见 [references/scoring-rubric.md](references/scoring-rubric.md)

### 4. 代码风格 (Code Style)

评估代码的可读性与规范性：
- **命名规范**：变量、函数、类命名是否语义清晰，符合约定
- **可读性**：代码结构是否直观，复杂度是否可控
- **注释质量**：必要处是否有注释，注释是否准确无冗余
- **代码组织**：文件结构、导入顺序、格式化是否符合规范

> 评分细则见 [references/scoring-rubric.md](references/scoring-rubric.md)

### 5. 代码质量 (Code Quality)

评估工程化与长期维护属性：
- **性能**：时间/空间复杂度是否合理，有无明显性能瓶颈
- **安全性**：是否存在注入、越权、敏感信息泄露等风险
- **可测试性**：是否易于单元测试，依赖是否可 mock
- **可维护性**：代码复杂度、重复度、变更成本
- **防御性编程**：输入校验、断言、容错处理

> 评分细则见 [references/scoring-rubric.md](references/scoring-rubric.md)

## 边界条件分析（强制）

在给出最终方案前，必须专门分析以下边界条件：
- **空值/空集合**：null、undefined、空数组、空字符串处理
- **极值**：最大值、最小值、整数溢出、超长字符串
- **并发边界**：竞态条件、死锁、资源耗尽
- **时序边界**：异步顺序、超时、重试、回调失败
- **权限边界**：未授权访问、越权操作、身份失效
- **数据边界**：格式错误、编码问题、脏数据、迁移兼容性
- **环境边界**：网络中断、磁盘满、内存不足、服务降级

## 评分与评级

**综合评分** = (软件设计 + 业务逻辑 + 代码逻辑 + 代码风格 + 代码质量) / 5

**评级**：
- 🏆 **卓越** (9.0 - 10)：方案成熟，可直接采用
- ✅ **优秀** (7.0 - 8.9)：方案良好， minor 调整即可
- ⚠️ **合格** (5.0 - 6.9)：方案可用，但存在需关注的问题
- ❌ **需改进** (< 5.0)：方案存在明显缺陷，建议重新设计

## 评估示例

### 示例：设计一个用户注册系统

```
## 📋 方案自我评估

### 需求理解
用户需要注册系统，核心需求：账号创建、密码安全、防重复注册。隐含需求：验证码防刷、密码强度、隐私合规。

### 方案概要
采用邮箱 + 密码注册，bcrypt 存储密码，Redis 限流防刷，邮箱验证激活。

### 五维评分

| 维度 | 得分 | 评估说明 |
|------|------|----------|
| 软件设计 | 8/10 | 分层清晰，但短信/邮箱通道未抽象统一 |
| 业务逻辑 | 9/10 | 覆盖注册、激活、防重，但密码找回未包含 |
| 代码逻辑 | 8/10 | 主逻辑正确，需补充邮箱格式严格校验 |
| 代码风格 | 9/10 | 命名清晰，结构规范 |
| 代码质量 | 7/10 | bcrypt 安全，但缺少 SQL 注入防御说明，限流粒度待细化 |

**综合评分：8.2 / 10** （评级：优秀）

### 边界条件分析
- [x] 空值/空集合处理：请求字段均做非空校验
- [x] 极值处理：密码长度限制 6-128 字符，邮箱长度限制 254 字符
- [ ] 并发安全：未处理并发重复提交，需加唯一索引或分布式锁
- [x] 时序与超时：验证码 5 分钟过期，激活链接 24 小时过期
- [x] 权限与授权：注册接口无需认证，但需图形验证码防刷
- [x] 数据兼容性：邮箱统一转小写存储，避免大小写重复
- [ ] 环境容错：Redis 宕机时注册流程降级策略未明确

### 风险提示与改进建议
1. **风险**：并发场景下可能出现重复账号
   **建议**：数据库加唯一索引（email），或注册时加分布式锁
2. **风险**：Redis 限流失效后可能被暴力注册
   **建议**：增加多级限流（IP + 邮箱），Redis 异常时降级为本地限流
3. **风险**：bcrypt 计算耗时可能被利用进行 DoS
   **建议**：设置 bcrypt 成本因子为 10-12，配合全局请求超时

### 替代方案
- 方案 B：手机号 + 验证码注册（适合国内场景，时效性高）
- 方案 C：OAuth 2.0 第三方登录（降低注册摩擦，适合 C 端）

---

## 📝 最终方案
[详细方案内容...]
```

## 不同场景的评估重点

### 系统架构设计
- 扩展性（水平/垂直扩展）
- 高可用性（冗余、故障转移）
- 数据一致性（CAP 权衡）
- 服务拆分粒度（微服务 vs 单体）

### 数据库设计
- 范式与反范式的平衡
- 索引与查询性能
- 分库分表与迁移策略
- 备份与恢复

### API 设计
- RESTful / RPC 规范
- 版本控制与兼容性
- 错误码与异常处理
- 限流、熔断、降级

### 算法/逻辑设计
- 时间/空间复杂度
- 边界条件与数学正确性
- 并发安全与原子性
- 可测试性与确定性

### 代码重构
- 行为一致性保持
- 测试覆盖率与回归风险
- 渐进式重构策略
- 回滚与兼容性

## 常见错误避免

### ❌ 避免的评估误区

1. **急于给出方案**
   - 未充分理解需求就开始设计
   - 忽略约束条件与边界

2. **评分虚高**
   - 未严格按维度扣分
   - 忽视已知风险仍给高分

3. **边界分析流于形式**
   - 只列边界项不做具体分析
   - 忽视并发与环境边界

4. **过度设计**
   - 为不存在的需求做设计
   - 过早优化或引入复杂架构

5. **技术堆砌**
   - 使用不熟悉或过度复杂的技术
   - 忽视团队维护能力

### ✅ 正确的评估习惯

1. **先问后答**：不确定时先澄清需求与约束
2. **诚实评分**：已知缺陷必须如实扣分并说明
3. **边界优先**：复杂场景先分析边界再写主逻辑
4. **小步验证**：复杂方案分阶段验证
5. **留有余地**：不过度承诺，明确方案局限

## 复杂方案评估流程

对于复杂方案，使用以下流程：

```
┌─────────────┐
│  理解需求   │
└──────┬──────┘
       ▼
┌─────────────┐
│  初步构思   │
└──────┬──────┘
       ▼
┌─────────────┐
│  五维自评   │
│  + 边界分析 │
└──────┬──────┘
       │ 评分 < 5 或存在致命缺陷
       ├────────────────► 调整方案
       │
       │ 评分 ≥ 5 且无致命缺陷
       ▼
┌─────────────┐
│  输出评分   │
│  与风险     │
└──────┬──────┘
       ▼
┌─────────────┐
│  输出最终   │
│  方案       │
└─────────────┘
```

## 连接指南：下一步该触发谁

- 用户说"方案不错，就这么做" → **→ [spec-driven-agent]**：进入 SDD 工作流，开始写 spec/plan/tasks 并执行
