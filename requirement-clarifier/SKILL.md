# Requirement Clarifier

## 核心原则

**用户给的往往不是需求，而是解决方案。**

"给我加个 Redis"是解决方案，真正的需求可能是"接口响应 P95 超过 2s"。如果不澄清就直接写 spec，可能用错误方案解决错误问题。

**澄清不是追问，是帮用户把脑子里的画面翻译出来。**

## 澄清流程

```
用户原始描述
    ↓
[1] 拆解显式需求      ←── 用户明确说出来的
    ↓
[2] 挖掘隐含需求      ←── 基于上下文推测的（标注"待确认"）
    ↓
[3] 识别缺失信息      ←── 写 spec 前必须知道但用户没说的
    ↓
[4] 列出待确认问题    ←── 用选择题或是否题降低用户回答成本
    ↓
[🛑 用户确认需求单]    ←── 用户明确点头后再进入 SDD
    ↓
移交 spec-driven-agent
```

## 禁止事项

- **禁止在需求未澄清时直接写 spec**。信息不够就硬写，产出的是幻觉 spec。
- **禁止用开放式问题轰炸用户**。"你有什么想法？"是烂问题；"A 方案和 B 方案你倾向哪个？"是好问题。
- **禁止替用户做假设**。所有假设必须标注"待确认"，等用户点头。

## 需求确认单格式

澄清完成后，必须输出以下内容：

```markdown
# 需求确认单

## 原始描述
<用户的原话，不做加工>

## 显式需求
- <用户明确说出来的目标 1>
- <用户明确说出来的目标 2>

## 隐含需求（待用户确认）
- [ ] <推测 1：基于上下文推断，需用户确认>
- [ ] <推测 2：...>

## 缺失信息
| 缺失项 | 为什么必须知道 | 当前假设 |
|--------|---------------|----------|
| <如：并发量> | <影响技术方案选型> | <待确认> |

## 待确认问题（请用户选择）
1. <问题 1，尽量给选项>
   - A. ...
   - B. ...
2. <问题 2>
   - 是 / 否

> **必须确认的构建信息**：
> - 项目构建系统（CMake / Makefile / build.sh / 其他）
> - 编译命令（如 `cmake --build build`、`make`、`./build.sh`）
> - 是否有已有的模块/库导入抽象（如 `AutoLibInclude.cmake`、`file(GLOB)` 等）
> - 新代码是否需要集成到现有构建流程中

## 范围初判
- **大概率要做**：<明确在范围内>
- **大概率不做**：<明确排除，防止蔓延>
- **待商榷**：<需讨论后决定>
```

## 需求确认单自评（内部质量门槛）

产出需求确认单后、呈现给用户前，必须执行一次内部自检。以下任一条件不满足，**禁止提交给用户**，必须先自我补充或追问用户：

| 检查项 | 通过标准 | 自检动作 |
|--------|---------|----------|
| **可写性** | 确认单的信息足以让下游写 spec，无需再追问用户 | 尝试在脑中草拟一段 spec 的"目标"和"验收标准"，若写不出来 → 信息不足 |
| **可验证性** | 每条显式需求至少包含"谁 + 做什么 + 达到什么效果"或可观测的输入/输出 | 检查是否存在"优化一下""完善一下"等无法验证的描述 |
| **边界清晰度** | 至少识别了 1 个明确约束（技术栈、版本兼容、性能、旧数据） | 若完全无约束 → 主动追问一条 |
| **假设暴露度** | 所有基于推测的内容都标注了"待确认"，没有隐式假设 | 逐条检查：这句话是用户亲口说的，还是我猜的？ |
| **构建信息** | 已确认或已追问项目的构建系统、编译命令、模块导入方式 | 若缺失 → 在待确认问题中补充 |

**自评未通过时的处理**：
- 信息不足 → 补充追问用户，更新待确认问题
- 可验证性差 → 重写该条需求，加入具体输入/输出或量化指标
- 假设未暴露 → 标注"待确认"，并说明推测依据

## 判断标准：可以移交 SDD 的信号

满足以下全部条件，才能进入 spec-driven-agent：
1. 核心目标至少有一句可验证的描述（谁 + 做什么 + 达到什么效果）
2. 关键输入和输出已明确（数据从哪来、产物流向哪）
3. 至少识别了 1-2 个明确的约束（时间、预算、技术栈）
4. 没有标注"待确认"的关键路径（可以留一些细节到 plan 阶段，但主线必须确认）

> 如果用户说"你先按这个理解做，有问题再改"——这是伪确认。必须至少把核心目标和验收标准落到纸上，让用户看到文字后明确同意。

## 连接指南：下一步该触发谁

本 Skill 的输出是**需求确认单**。用户确认后，工作流应移交：

**→ [spec-driven-dev]**：进入 SDD 工作流，按任务分级（S/M/L）产出设计产物（S 档：确认单+tasks 即设计，免独立设计文档；M/L 档：spec-plan.md + tasks.md）

> 不要在本 Skill 中提前写 spec 或技术方案。需求确认单是终点，SDD 是下一棒。
> 确认单必须注明**拟定档位（S/M/L）及理由**——用户确认需求即确认档位。
