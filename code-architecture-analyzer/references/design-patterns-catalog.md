# 设计模式识别指南

本文档供 code-architecture-analyzer 在扫描代码时参考，用于识别代码中应用的设计模式。识别时应遵循"结构特征 + 意图验证"两步法，避免仅因结构相似就判定为某模式。

## 识别原则

1. **结构特征先行**：代码结构符合某模式的典型实现形式
2. **意图验证**：该结构确实用于解决该模式旨在解决的问题
3. **避免误识别**：装饰器模式与代理模式结构相似，需通过意图区分
4. **标注评价**：识别后评价使用是否恰当，是否存在过度设计

---

## 创建型模式

### 单例模式（Singleton）

**结构特征**：
- 类有私有的静态实例字段
- 构造函数为 private 或 protected
- 提供公共的静态获取方法（`getInstance()`）

**常见实现**：
- 饿汉式：静态字段直接初始化
- 懒汉式：静态字段延迟初始化 + 同步锁 / DCL / 静态内部类
- 枚举实现（Java）

**意图验证**：确保该实例确实代表"全局唯一"的某种资源或状态

**误用信号**：
- 单例类持有大量可变状态 → 本质上是全局变量，难以测试
- 单例类职责不单一 → 变成了 God Object

---

### 工厂模式（Factory）

**结构特征**：
- 工厂类/方法根据参数创建不同具体类的实例
- 客户端不直接使用 `new ConcreteClass()`，而是通过工厂方法

**变体识别**：
- **简单工厂**：单一工厂方法，根据 switch/if 返回不同实例
- **工厂方法**：抽象 Creator + 具体 Creator，子类决定实例化哪个类
- **抽象工厂**：多个相关产品的创建接口，具体工厂实现一组产品

**意图验证**：创建逻辑确实需要解耦，而非多余的间接层

---

### 建造者模式（Builder）

**结构特征**：
- 有 Builder 内部类或独立 Builder 类
- Builder 提供链式调用方法（`withXxx()` / `setXxx()`）
- 最终通过 `build()` 方法创建目标对象

**常见场景**：
- 构造参数过多（>4 个）
- 需要分步构建或可选参数组合
- 构造过程需要校验逻辑

---

### 原型模式（Prototype）

**结构特征**：
- 类实现 `clone()` / `copy()` / `Cloneable` 接口
- 通过复制现有对象创建新对象

**常见场景**：
- 对象创建成本高，复制更轻量
- 需要保留对象历史状态

---

## 结构型模式

### 适配器模式（Adapter）

**结构特征**：
- 存在 Adapter 类实现了目标接口
- Adapter 内部持有被适配者的引用
- 将目标接口的调用转换为被适配者的接口调用

**意图验证**：确实用于兼容两个不兼容的接口，而非简单的封装

---

### 装饰器模式（Decorator）

**结构特征**：
- 装饰器类与被装饰类实现同一接口/继承同一抽象类
- 装饰器持有被装饰对象的引用（组合）
- 可在调用前后添加行为

**与代理模式的区别**：
- 装饰器：动态添加职责，通常可嵌套多层
- 代理：控制对对象的访问，通常为一对一

---

### 代理模式（Proxy）

**结构特征**：
- 代理类与真实主题实现同一接口
- 代理持有真实主题的引用，控制对其的访问

**变体识别**：
- **远程代理**：处理网络通信（如 RPC Stub）
- **虚拟代理**：延迟加载（如图片占位、大数据对象）
- **保护代理**：权限控制
- **缓存代理**：结果缓存

---

### 门面模式（Facade）

**结构特征**：
- 提供一个统一的简化接口
- 门面内部封装了对多个子系统接口的调用

**常见命名**：`XxxFacade`、`XxxService`、`XxxManager`

---

### 组合模式（Composite）

**结构特征**：
- 树形结构，叶子节点和容器节点实现同一接口
- 容器节点可包含子节点列表

**常见场景**：
- UI 组件树、文件系统、组织结构、AST

---

## 行为型模式

### 观察者模式（Observer）

**结构特征**：
- 存在 Subject（被观察者）和 Observer（观察者）接口
- Subject 维护 Observer 列表，状态变化时通知所有 Observer
- 常见实现：事件监听、发布订阅、回调函数注册

**现代变体**：
- EventEmitter / EventBus
- RxJS Observable
- Spring ApplicationEvent

---

### 策略模式（Strategy）

**结构特征**：
- 定义策略接口/抽象类
- 多个具体策略实现该接口
- 上下文（Context）持有策略引用，运行时切换

**常见场景**：
- 排序算法切换、支付方式切换、压缩算法切换
- 若用 if/else/switch 处理同类行为的不同变体，可能是策略模式的替换机会

---

### 模板方法模式（Template Method）

**结构特征**：
- 抽象类定义算法骨架
- 具体步骤由子类实现（抽象方法或钩子方法）
- 子类不改变算法结构，只改变某些步骤

**常见场景**：
- 框架中的生命周期方法、数据处理的固定流程

---

### 命令模式（Command）

**结构特征**：
- 将请求封装为对象（Command 接口 + 具体 Command）
- 支持撤销、队列、日志

**常见场景**：
- undo/redo 系统、任务队列、事务管理

---

### 责任链模式（Chain of Responsibility）

**结构特征**：
- 多个处理器连成链
- 每个处理器决定处理请求或传递给下一个

**常见场景**：
- 中间件链（Express/Koa）、拦截器链、审批流程

---

## 架构模式

### 分层架构（Layered Architecture）

**识别特征**：
- 代码按层组织：表现层 / 业务层 / 数据访问层
- 层间单向依赖（上层依赖下层）
- 禁止跨层调用

---

### MVC / MVP / MVVM

**MVC**：
- Model（数据）、View（UI）、Controller（调度）
- Controller 接收输入，操作 Model，选择 View

**MVVM**：
- ViewModel 通过双向绑定与 View 同步
- 常见：前端框架（Vue、Angular）

---

### 微服务架构

**识别特征**：
- 代码按服务拆分，独立仓库或目录
- 服务间通过 API / 消息队列通信
- 独立部署、独立数据库

---

### 事件驱动架构（Event-Driven）

**识别特征**：
- 组件间通过事件/消息异步通信
- 存在 Event Bus / Message Broker
- 发布者不知订阅者是谁

---

### 六边形架构 / 端口适配器

**识别特征**：
- 核心领域逻辑位于中心
- 端口（接口）定义外部交互契约
- 适配器实现端口，隔离外部技术细节
- 依赖方向：向内指向领域层

---

### CQRS（命令查询职责分离）

**识别特征**：
- 写模型和读模型分离
- 命令（修改）走一条路径，查询（读取）走另一条路径
- 常配合事件溯源使用

---

## 识别评价标准

识别出模式后，按以下标准评价：

| 评价 | 标准 |
|------|------|
| ✅ 恰当 | 模式解决了实际问题，结构清晰，无过度设计 |
| ⚠️ 可用但有改进空间 | 模式有效，但实现有瑕疵（如缺少接口抽象、硬编码） |
| ❌ 误用/过度设计 | 为简单场景引入复杂模式，或实现不符合模式意图 |
| ❓ 疑似但未确认 | 结构类似但无法确认意图，需标注为"疑似" |
