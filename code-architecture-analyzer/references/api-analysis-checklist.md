# API 分析检查清单

本文档供 code-architecture-analyzer 在分析项目 API 接口时参考，确保分析维度完整、结论可追溯。

## 分析流程

```
接口发现（扫描路由定义、Controller、OpenAPI 文档）
        ↓
    契约分析（参数、响应、错误码）
        ↓
    规范检查（RESTful、安全性、版本）
        ↓
    质量评估（一致性、完整性、可维护性）
```

---

## 1. 接口发现

**扫描目标**：
- Web 框架路由定义（Spring `@RequestMapping`、Express `app.get()`、FastAPI `@app.get()` 等）
- OpenAPI / Swagger 文档（`openapi.yaml`、注解生成的文档）
- gRPC proto 文件
- GraphQL schema 文件

**输出**：接口清单表

| 方法 | 路径 | 描述 | 所在文件 | 路由定义行号 |
|------|------|------|----------|-------------|
| | | | | |

---

## 2. 契约分析

### 2.1 请求分析

**检查项**：
- [ ] 请求方法（GET/POST/PUT/DELETE/PATCH）是否符合 HTTP 语义
- [ ] 路径设计是否资源导向（`/users/{id}` 而非 `/getUser`）
- [ ] 路径参数、查询参数、请求体的使用是否合理
- [ ] 参数类型定义是否明确（string / int / bool / object / array）
- [ ] 必填参数与可选参数是否区分
- [ ] 参数校验规则是否完整（长度限制、格式正则、取值范围）

### 2.2 响应分析

**检查项**：
- [ ] 响应结构是否统一（统一包装 `{code, data, message}` 或裸返回）
- [ ] 状态码使用是否符合语义（200/201/204/400/401/403/404/500 等）
- [ ] 响应字段类型是否明确
- [ ] 分页接口是否遵循统一分页结构

**分页结构参考**：
```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 100,
    "totalPages": 5
  }
}
```

### 2.3 错误码分析

**检查项**：
- [ ] 错误码是否统一设计（业务错误码 vs HTTP 状态码）
- [ ] 同一类错误是否使用一致的错误码
- [ ] 错误信息是否对调用方友好（不泄露内部实现细节）
- [ ] 是否包含错误追踪标识（traceId / requestId）

**错误响应结构参考**：
```json
{
  "code": 10001,
  "message": "用户不存在",
  "traceId": "abc123",
  "details": {
    "field": "userId",
    "value": "99999"
  }
}
```

## 3. 规范检查

### 3.1 RESTful 规范

| 检查项 | 通过标准 |
|--------|----------|
| 资源命名 | 名词复数形式，小写字母，连字符分隔（kebab-case） |
| HTTP 方法语义 | GET=查询，POST=创建，PUT=全量更新，PATCH=部分更新，DELETE=删除 |
| 状态码 | 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 500 Internal Error |
| 幂等性 | GET/PUT/DELETE 是否幂等，POST 是否非幂等且有防重机制 |
| 过滤/排序/分页 | 是否通过查询参数实现（`?status=active&sort=name&page=1`） |

### 3.2 安全性

**检查项**：
- [ ] 认证机制：Token / Session / OAuth / JWT，是否所有敏感接口都受保护
- [ ] 鉴权粒度：接口级别是否有权限校验（RBAC / ABAC）
- [ ] 输入校验：是否防范 SQL 注入、XSS、命令注入
- [ ] 敏感数据：密码、Token、身份证号等是否加密传输（HTTPS）和存储
- [ ] 限流策略：是否有接口级别的限流（QPS / 并发数）
- [ ] CORS 配置：跨域策略是否合理，不过度开放

### 3.3 版本管理

**检查项**：
- [ ] 是否有版本策略（URL 路径 `/v1/`、Header `Accept-Version`、Content-Type）
- [ ] 版本升级时是否保证向后兼容
- [ ] 弃用接口是否有明确标记和迁移文档

**版本策略对比**：

| 策略 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| URL 路径 | `/api/v1/users` | 直观，便于缓存 | URL 臃肿 |
| Header | `Accept-Version: v1` | URL 干净 | 需要文档说明 |
| Content-Type | `application/vnd.api.v1+json` | 规范 | 复杂度高 |

## 4. 质量评估

### 4.1 一致性

- [ ] 同类型接口的响应结构是否一致
- [ ] 错误码体系是否统一
- [ ] 命名规范是否统一（驼峰 vs 下划线、单复数一致性）
- [ ] 时间格式是否统一（ISO 8601 / Unix 时间戳）

### 4.2 完整性

- [ ] 核心业务流程是否都有对应的接口覆盖
- [ ] 接口文档是否包含参数说明、示例、错误场景
- [ ] 是否有 OpenAPI / Swagger / Postman 集合

### 4.3 可维护性

- [ ] 接口数量是否合理（避免过度拆分或 God Endpoint）
- [ ] 是否可测试（是否有测试接口、Mock 数据支持）
- [ ] 接口变更是否会影响大量调用方（耦合度评估）
