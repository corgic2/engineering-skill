# Code Architecture Analyzer

对现有代码库进行系统性架构分析，识别模块结构、设计模式、API 契约和数据流，输出标准化的架构设计文档。

## 分工边界

- **分析现有代码并输出文档** → 触发本 Skill
- **基于分析结果进行代码重构/开发** → 触发 spec-driven-agent
- **纯技术方案评审（不涉及代码扫描）** → 触发 solution-validator
- **代码质量审查（已有产出代码）** → 触发 code-review

## 核心原则

1. **代码优先于推测**：一切结论必须能从代码中追溯到具体文件和行号，禁止凭空臆测未使用的模块或设计意图
2. **图是分析的产物，不是目的**：只在需要表达复杂关系时绘制 Mermaid 图，避免为简单逻辑画图
3. **保持客观**：区分"代码实际做了什么"和"设计应该怎么做"，在文档中明确标注观察到的设计与理想设计的差距
4. **渐进式深度**：先宏观（目录结构、模块边界），再微观（类关系、函数调用链），避免一次性陷入细节

## 四步分析工作流

```
代码扫描与上下文收集
        ↓
    架构分析（模块/依赖/分层）
        ↓
    流程图与模式分析（Mermaid + 设计模式识别）
        ↓
    生成架构设计文档
```

### Step 1: 代码扫描与上下文收集

**目标**：建立代码库的全局视图，确定分析范围。

**执行动作**：
1. 扫描项目根目录结构，识别技术栈（语言、框架、构建工具）
2. 读取关键配置文件：`package.json`、`pom.xml`、`Cargo.toml`、`go.mod`、`CMakeLists.txt` 等
3. 识别主要源码目录和入口点（`main()`、`index.js`、`app.py` 等）
4. 识别测试目录结构，了解测试覆盖的模块范围
5. **规模判断**：估算源码文件数和核心模块数
   - 小型（<50 个源码文件）：全量分析
   - 中型（50-200 个）：全量分析，复杂模块可简化
   - 大型（>200 个）：与用户确认优先分析的 1-3 个核心模块或核心流程
   - 超大型（>1000 个）：采用分层抽样策略——先分析顶层目录结构，再深入 1-2 个代表性模块
6. 若分析范围受限，在文档中明确标注"分析范围"和"未覆盖模块"

**输出**：
- 项目技术栈概述（语言、框架、构建工具）
- 目录结构摘要（主要模块及其职责推断）
- 分析范围确认（全量或指定模块）

### Step 2: 架构分析

**目标**：识别模块边界、依赖关系、分层设计和关键抽象。

**分析维度**：

| 维度 | 关注点 | 追溯要求 |
|------|--------|----------|
| 模块划分 | 目录/包/命名空间如何组织，每个模块的职责 | 标注关键目录和代表文件 |
| 依赖关系 | 模块间 import/include 关系，循环依赖 | 标注核心依赖链的文件路径 |
| 分层设计 | 是否遵循分层架构（表现层/业务层/数据层） | 标注各层的典型文件 |
| 接口抽象 | 抽象类、接口、trait 的定义与实现关系 | 标注接口定义位置和主要实现类 |
| 数据流 | 核心数据类型如何在模块间传递 | 标注关键 DTO/Model/Entity 文件 |

**输出**：
- 模块职责表
- 依赖关系矩阵（或 Mermaid 依赖图）
- 分层架构图（若适用）
- 关键接口列表

### Step 3: 流程图与设计模式分析

**目标**：可视化核心流程，识别代码中的设计模式应用。

#### 3.1 流程图分析

当分析涉及 3 个以上模块交互、状态转换或异步流程时，必须绘制 Mermaid 图。

**图表类型选择**（参照 mermaid-diagrams Skill）：

| 场景 | 图表类型 | 示例 |
|------|----------|------|
| 模块/服务调用链 | flowchart TD/LR | 请求处理全流程 |
| 类继承与组合关系 | classDiagram | 领域模型类关系 |
| 请求-应答时序 | sequenceDiagram | API 调用时序 |
| 状态生命周期 | stateDiagram-v2 | 订单状态流转 |

**规范**：
- 每张图不超过 15 个节点，复杂流程拆分
- 节点文本标注对应代码位置（如 `// 见 OrderService.java:45`）
- 条件分支的方向（是/否）与代码中的 if/else 一致
- 输出图后执行一致性检查：函数名、文件路径、调用顺序是否与代码一致

#### 3.2 设计模式识别

基于代码结构特征识别设计模式。详见 [references/design-patterns-catalog.md](references/design-patterns-catalog.md)。

**识别流程**：
1. 扫描代码中符合某模式特征的结构（如单一静态实例 → 单例模式）
2. 验证该结构是否确实按模式的意图使用（避免误识别）
3. 标注模式的应用位置、意图和效果
4. 若存在模式的误用或过度设计，在文档中标注为"改进建议"

**输出**：
- 核心流程 Mermaid 图（调用链、数据流、时序图）
- 设计模式清单（模式名、应用位置、使用评价）
- 架构模式判定（MVC、微服务、事件驱动、CQRS 等）

### Step 4: 生成架构设计文档

**目标**：将所有分析结果整合为一份标准化的架构设计文档。

**文档输出位置**：
- **默认路径**：项目根目录下的 `docs/` 文件夹（如 `docs/architecture-design.md`）
- 若项目根目录不存在 `docs/` 文件夹，**必须主动创建**
- 若用户指定了其他文档目录，按用户要求执行
- 禁止将架构文档散落在 `Agentic/` 子目录或临时目录中，确保文档可被团队成员持续发现和维护

**文档结构**（详见 [references/architecture-doc-template.md](references/architecture-doc-template.md)，输出示例见 [references/example-output.md](references/example-output.md)）：

```markdown
# <系统名> 架构设计文档

## 1. 文档信息
- 版本、日期、作者、适用范围

## 2. 系统概述
- 业务背景、系统定位、核心能力

## 3. 架构视图
### 3.1 逻辑视图（模块结构与依赖）
### 3.2 进程视图（运行时交互）
### 3.3 部署视图（物理拓扑）

## 4. 模块设计
- 每个模块的职责、关键类、对外接口

## 5. 数据流设计
- 核心业务流程的 Mermaid 图 + 文字说明

## 6. API 设计
- 接口清单、契约说明（详见 [references/api-analysis-checklist.md](references/api-analysis-checklist.md)）

## 7. 设计模式
- 已识别的模式清单及评价

## 8. 非功能性设计
- 性能、安全、扩展性、可维护性评估

## 9. 风险与改进建议
- 观察到的架构债务、耦合问题、改进方向
```

**输出要求**：
- 文档必须能从代码中追溯，每个关键结论标注来源文件
- Mermaid 图与代码实现保持一致（函数名、路径、调用链）
- 区分"现状描述"和"改进建议"，后者明确标注

## API 分析专项指南

当用户需要分析 API 接口时，按以下维度执行（详见 [references/api-analysis-checklist.md](references/api-analysis-checklist.md)）：

1. **接口契约**：URL/方法、请求参数、响应结构、状态码
2. **规范符合性**：RESTful 原则、HTTP 方法语义、资源命名
3. **安全性**：认证方式、鉴权粒度、敏感信息处理、限流策略
4. **版本管理**：版本策略（URL/Header/Content-Type）、兼容性
5. **文档完整性**：是否有 OpenAPI/Swagger、参数说明、示例

## 一致性检查清单

输出最终文档前，逐条核对：

- [ ] 文档中每个模块/类名与代码中的实际名称一致
- [ ] Mermaid 图中的每个函数名、文件路径与代码一致
- [ ] 流程图中的条件分支方向与代码中的 if/else 逻辑一致
- [ ] 时序图中的消息顺序与代码执行顺序一致
- [ ] 每个设计模式的识别都有代码中的具体结构支撑
- [ ] API 接口的 URL、参数、响应与代码中的实际定义一致
- [ ] 所有"改进建议"都明确标注，不与"现状描述"混淆
- [ ] 单张 Mermaid 图节点数不超过 15 个

## 连接指南

### 入口
- 用户直接提供代码库路径，要求"分析架构""生成架构文档"
- 用户要求"分析这个项目的模块依赖"
- 用户要求"画出这个系统的调用流程"
- 用户要求"分析这个项目的 API 设计"
- `spec-driven-dev` 旁路中判断为纯代码结构分析时触发

### 出口
- 分析完成，用户确认文档 → 交付文档，任务结束
- 用户要求"基于分析结果进行重构" → 触发 **spec-driven-agent**，将架构文档作为输入
- 用户要求"审查这个架构设计" → 触发 **solution-validator**
- 用户要求"review 产出的文档" → 触发 **code-review**
