# SDD 文档完整模板

可直接复制使用的 spec / plan / tasks / constitution 模板。根据项目实际调整字段。

> **物理文件组织以 spec-driven-dev 任务分级（S/M/L）为准**：S 档免独立设计文档（确认单+tasks 即设计）；M/L 档 spec 与 plan 合并为 `spec-plan.md`（spec 内容在前、plan 内容在后，测试策略并入「验证方案」章节）；`tasks.md` 只留勾选项（id/标题/状态/涉及文件/一句话完成标准），不复述步骤细节。以下模板按逻辑内容使用，不按文件名一一对应。

---

## spec.md — 规格说明

```markdown
# Spec: <一句话目标>

## 背景
<用户反馈、业务背景或问题描述，引用原始表述>

## 目标
<用可验证的语言描述，避免"优化""完善"等模糊词，改用"P95 从 800ms 降到 200ms">

## 验收标准（必须可检查）
- [ ] <标准 1：具体输入 + 预期输出>
- [ ] <标准 2：边界行为，如空列表、超长大文本>
- [ ] <标准 3：性能/体验/兼容性要求>

## 约束与范围
- **做**：<明确包含的内容>
- **不做**：<明确排除的内容，防止范围蔓延>
- **资源上限**：<可选：时间、成本、调用次数限制>

## 参考
- <相关链接、历史 issue、设计文档>
```

## plan.md — 技术方案

```markdown
# Plan: <对应 spec 标题>

## 分析
<问题根因或实现思路，控制在 3 段以内>

## 涉及文件
| 文件路径 | 操作 | 说明 |
|----------|------|------|
| `path/to/file` | 修改 | <改什么> |
| `path/to/new` | 新增 | <做什么> |

## 设计约束（不可偏离，偏离需记录并确认）
| 约束项 | 要求 | 验收方式 |
|--------|------|---------|
| PIMPL / 封装 | <如：头文件不得暴露第三方库类型> | <如何检查> |
| 接口格式 | <如：prompt 使用 [USER]/[ASSISTANT] 格式> | <如何检查> |
| 类职责 | <如：扫描逻辑必须在 ModelManager 类中> | <如何检查> |

## 实现步骤
1. <步骤 1，明确输入输出>
2. <步骤 2，依赖步骤 1>
3. <步骤 3，验证方式>

## 并发与线程模型
- [ ] 数据库操作是否涉及多线程？后台线程使用什么连接策略？
- [ ] 若使用异步（ThreadPool / QtConcurrent / QThread），底层数据库连接是否线程安全？
- [ ] UI 敏感操作的响应时间要求？（>100ms 的操作必须异步，但需确保线程安全）
- [ ] 旧数据迁移方案：若变更表结构，已有数据库如何升级？

## 风险评估
- <可能引入的副作用>
- <回退方案：如果失败，如何恢复到之前状态>

## 验证计划
- <如何确认验收标准全部达成>
```

## tasks.md — 任务清单

```markdown
# Tasks: <对应 plan 标题>

## 任务列表

### Task 1: <简短描述>
- **状态**: `pending | in_progress | done | failed`
- **负责人**: <agent / human>
- **输入**: <明确的上下文或文件>
- **输出**: <预期产物，含文件路径>
- **完成标准**: <可验证的条件>
- **设计约束检查**: <与 spec-plan.md "设计约束"逐项对齐，确认无偏离>
- **涉及文件核对**: <执行完成后，用 `git diff --name-only` 核对实际修改文件是否与 plan 一致>
- **依赖**: <无 / Task X>

### Task 2: <简短描述>
- **状态**: `pending`
- **输入**: ...
- **输出**: ...
- **完成标准**: ...
- **依赖**: Task 1

## 执行记录
- <YYYY-MM-DD HH:MM>: <发生了什么，包括失败和重试原因>
```

## constitution.md — 架构约束

```markdown
# Constitution: <项目名> 架构约束

## 目录结构约定
- `src/components/` — 仅放展示组件，禁止放业务逻辑
- `src/services/` — 仅放 API 调用层
- `tests/unit/` — 单元测试，按模块镜像目录

## 模块边界
- 前端组件禁止直接调用数据库
- 公共工具函数必须写在 `src/utils/` 并通过单测
- 配置文件与业务代码分离

## 命名规则
- 组件：PascalCase
- 工具函数：camelCase
- 常量：SCREAMING_SNAKE_CASE

## 代码审查红线
- 禁止三层抽象解决一个函数能搞定的问题
- 禁止重复工具方法散落在多个文件
- 禁止修改没有留下 spec-plan.md 的既有模块
```
