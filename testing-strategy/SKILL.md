# Testing Strategy

## 核心原则

**测试不是开发的附属品，是需求的一部分。**

可验证性（可测试性）是代码质量的核心维度。如果一段代码无法方便地验证其正确性，那它的"正确"只是假象。

### 测试优先原则

- 在 `spec-driven-agent` 产出 `plan.md` 时，**每个涉及业务逻辑的 Task 必须伴随测试验证方案**
- 在 `code-review` 的"可验证性"维度中，**没有测试覆盖的关键路径必须扣分**
- 边界条件不是"顺带测一下"，而是**必须显式设计用例**

## 触发与衔接

### 入口
- 用户说"帮我写测试""这里需要补测试用例"
- `spec-driven-agent` 设计阶段，需要在 plan.md 中补充测试 Task
- `code-review` 发现关键路径无可验证手段，需要补充测试设计

### 出口
- 产出测试方案后 → 回到 **spec-driven-agent** 或 **code-review** 继续流程
- 用户仅需要测试建议（不动代码）→ 作为咨询交付，不入开发流程

## 测试设计四步法

```
识别测试目标
    ↓
选择测试类型（单元 / 集成 / 边界 / 回归）
    ↓
设计用例（输入 + 预期输出 + 通过标准）
    ↓
评估覆盖度与优先级
```

### Step 1: 识别测试目标

明确要验证什么：

| 问题 | 说明 |
|------|------|
| 测什么功能？ | 核心业务流程、新增接口、修复的 bug |
| 测什么层级？ | 纯函数 → 单元测试；模块交互 → 集成测试；端到端 → 系统测试 |
| 测什么属性？ | 正确性、性能、异常恢复、并发安全 |

### Step 2: 选择测试类型

| 类型 | 适用场景 | 典型粒度 |
|------|---------|---------|
| **单元测试** | 验证单个函数/类的行为 | 函数级、类方法级 |
| **集成测试** | 验证模块间协作 | 多模块调用链、数据库交互 |
| **边界测试** | 验证临界条件、异常输入 | 空值、越界、极值、空集合 |
| **状态测试** | 验证状态机转换 | 生命周期、协议状态 |
| **回归测试** | 防止修复引入新问题 | 历史 bug 场景复现 |
| **并发测试** | 验证多线程/异步安全 | 竞态条件、死锁、资源泄漏 |
| **端到端测试 (E2E)** | 从用户视角验证完整业务流程 | 核心用户场景、关键 UI/接口流程、发布前验收 |

### Step 3: 设计用例

每个用例必须包含：

```markdown
### 用例: <简明描述>
- **目标**: <验证的具体行为>
- **输入**: <具体输入值或前置状态>
- **预期输出**: <明确的预期结果>
- **通过标准**: <可自动或手动验证的判断条件>
- **优先级**: P0(阻塞) / P1(重要) / P2(一般)
```

#### 用例设计技术

**等价类划分**
- 将输入域划分为若干等价类，每类选一个代表测试
- 示例：年龄字段 → 有效等价类 `[0, 150]`，无效等价类 `< 0`、`> 150`、非数字

**边界值分析**
- 重点测试等价类的边界及边界两侧
- 示例：数组长度限制 100 → 测试 0、1、99、100、101

**状态转换**
- 对状态机：列出所有状态，验证每对合法/非法转换
- 示例：连接状态 `DISCONNECTED → CONNECTING → CONNECTED → DISCONNECTED`

**错误推测**
- 基于经验预测易错点：空指针、除零、类型转换、资源未释放

### Step 4: 评估覆盖度

产出测试方案后，用以下清单自评：

- [ ] **主路径覆盖**：每个正常业务流程至少有一个正向用例
- [ ] **边界覆盖**：所有数值/长度/容量限制都测了边界及两侧
- [ ] **异常覆盖**：每个可能抛出异常/返回错误的场景都有用例
- [ ] **空值覆盖**：所有指针/引用/可选参数都测了 null/空值
- [ ] **分支覆盖**：条件语句的每个分支（if/else、switch/case）都有对应用例
- [ ] **并发覆盖**：涉及共享状态/资源的操作，有并发场景验证
- [ ] **回归覆盖**：历史 bug 修复点有对应回归用例
- [ ] **端到端覆盖**：每个核心用户流程至少有一个从入口到出口的 E2E 用例

## 测试产物存放规范

**测试设计文档必须与 SDD 产物放在一起，禁止散落在代码目录中。**

### 存放原则

| 产物类型 | 存放位置 | 说明 |
|---------|---------|------|
| 测试用例文档 (`test-cases.md`) | `Agentic/sdd/<需求名称>/`（或项目约定的 `sdd/<需求名称>/`） | 与 spec/plan/tasks 同级，作为 SDD 设计产物 |
| 测试策略说明 (`test-strategy.md`) | `Agentic/sdd/<需求名称>/` | 测试类型选择、覆盖度目标、风险评估 |
| 测试覆盖度报告 (`coverage-report.md`) | `Agentic/sdd/<需求名称>/` | 执行后回填的覆盖度评估 |
| **可执行测试代码**（`.cpp` / `.py` / `.test.js` 等） | 按项目既有规范（如 `tests/`、`src/__tests__/`） | 唯一进入代码仓库的测试相关文件 |

### 禁止行为

- ❌ **禁止**将测试用例列表、测试设计思路写成注释或 Markdown 文件，散落在源码目录
- ❌ **禁止**在代码文件目录中创建 `test-notes.md`、`test-plan.md` 等临时文档
- ❌ **禁止**把测试策略作为代码注释写在源文件顶部

### 规范示例

假设当前需求为"修复搜索分页 bug"，SDD 目录为 `Agentic/sdd/fix-search-pagination/`：

```
Agentic/sdd/fix-search-pagination/
├── workflow-state.md
├── spec.md
├── plan.md
├── tasks.md
├── test-cases.md          ← 本 Skill 产出的用例文档
├── test-strategy.md       ← 测试策略与覆盖度目标
└── coverage-report.md     ← 执行后回填的覆盖度报告
```

`test-cases.md` 内容参见 [references/test-case-template.md](references/test-case-template.md)，包含完整用例模板与编号规范。

## 与 SDD 流程的协作

### 在 plan.md 中嵌入测试

`spec-driven-agent` 设计阶段，测试任务应作为独立 Task 或每个 Task 的完成标准之一：

```markdown
### Task 3: 实现订单状态转换逻辑
- **状态**: pending
- **输入**: 订单当前状态 + 操作事件
- **输出**: 状态机实现代码
- **完成标准**:
    - [ ] 代码实现完成
    - [ ] 单元测试覆盖所有状态转换（见 test-cases.md）
    - [ ] 边界测试：非法转换返回错误
    - [ ] 回归测试：历史 bug #123 场景通过
```

> **引用规范**：plan.md / tasks.md 中引用测试产物时，使用相对路径 `test-cases.md`，而非绝对路径或代码目录路径。

### 在 code-review 中检查可验证性

`code-review` 审查时，对测试相关维度重点检查：

| 检查项 | 不通过标准 |
|--------|-----------|
| 关键路径无测试 | 核心业务逻辑缺少单元测试或集成测试 |
| 测试无法运行 | 测试依赖未声明的环境/数据，无法在干净环境运行 |
| 测试断言模糊 | 使用"优化""正常"等不可验证的描述作为通过标准 |
| 边界未覆盖 | 有空指针、越界、空集合风险但无对应测试 |
| Mock 过度 | 所有依赖都被 Mock，测不到真实交互问题 |
| 核心流程无 E2E | 关键用户场景没有端到端用例，只在函数/模块层验证 |
| E2E 依赖未声明 | 端到端测试依赖未记录的外部服务、固定数据或人工干预 |

## 测试代码质量规范

1. **测试名即文档**：`test_calculatePrice_withNegativeQuantity_returnsError` 优于 `test1`
2. **独立可重复**：测试之间无顺序依赖，可单独运行
3. **快速反馈**：单元测试应在秒级完成，慢测试放集成测试集
4. **明确断言**：一个测试验证一个概念，避免"测了 5 件事，失败不知道是哪件"
5. **生产代码同等标准**：测试代码也要有可读性，禁止复制粘贴大量重复 setup

## 端到端测试设计原则

端到端测试不是为了替代单元/集成测试，而是为了回答**"用户能不能完整完成这件事"**。

1. **场景优先，而非 UI 穷尽**：每个 E2E 用例对应一个用户目标（如"登录后下单"），而不是每个按钮点一遍。
2. **主流程优先**：先覆盖 P0  happy path，再考虑异常分支。E2E 用例不是越多越好。
3. **独立可重复**：每个用例自己准备和清理数据，不能依赖其他测试留下的状态。
4. **减少脆弱定位**：优先使用语义化选择器（如 role、test-id），避免依赖易变的 CSS 类名或 DOM 层级。
5. **明确失败含义**：E2E 失败时应能判断是产品 bug、测试数据问题还是环境不稳定。

## 常见陷阱

### ❌ 陷阱 1：只测"正常情况"
```cpp
// ❌ 只测正常输入
TEST(Calc, Normal) {
    EXPECT_EQ(calc.add(2, 3), 5);
}

// ✅ 必须补充边界和异常
TEST(Calc, Overflow) {
    EXPECT_THROW(calc.add(INT_MAX, 1), OverflowError);
}
```

### ❌ 陷阱 2：测试与实现耦合过深
```cpp
// ❌ 测试验证了私有实现细节
EXPECT_EQ(obj.internal_counter_, 5);  // 重构时必崩

// ✅ 测试只验证公开行为
EXPECT_EQ(obj.getResult(), expected);
```

### ❌ 陷阱 3：依赖全局状态
```cpp
// ❌ 测试 A 修改了全局配置，测试 B 失败
Config::setTimeout(100);  // 影响其他测试

// ✅ 每个测试独立 setup/teardown
```

## 连接指南

### 入口
- 用户说"帮我写测试""补测试用例"
- `spec-driven-agent` 设计阶段，需要在 plan.md 中补充测试验证方案
- `code-review` 发现关键路径无可验证手段，需要补充测试设计

### 出口
- 测试方案产出后 → 回到 **spec-driven-agent** 更新 plan.md / tasks.md
- 审查阶段补充测试 → 回到 **code-review** 更新可验证性维度评分
- 验收阶段 → 对照 `test-cases.md` 逐条确认

```
开发流程中的测试介入点：

spec-driven-agent 写 plan.md
    ↓
[本 Skill 介入] → 为关键 Task 设计测试方案 → 更新 plan.md / tasks.md
    ↓
代码执行（按 tasks 执行，含测试编码）
    ↓
编译验证（测试必须编译通过）
    ↓
code-review（检查可验证性维度）
    ↓
验收（对照 test-cases.md 逐条确认）
```
