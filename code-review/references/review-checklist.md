# 代码审查完整检查清单

执行审查时逐条核对，避免遗漏。

## 审查范围拆分规则

**按审查深度和注意力负荷控制单批次范围**。

审查质量与单批次文件数成反比。若变更范围较大，按以下原则拆分：

| 批次 | 优先级 | 包含内容 |
|------|--------|---------|
| 第 1 批 | P0 | 核心逻辑文件（状态机、算法、数据流） |
| 第 2 批 | P1 | 接口层文件（对外 API、协议序列化） |
| 第 3 批 | P2 | 辅助文件（工具函数、配置、文档） |

**拆分原则**：
- **深度优先于广度**：宁可少审几个文件，也要保证每个文件审透（正常路径、异常路径、边界条件）
- **核心优先于外围**：P0 批次必须优先完成，确保关键逻辑无重大缺陷后再审查辅助文件
- **上下文窗口为硬约束**：若使用 Agent/模型审查，单批次范围不得超过其有效上下文容量（超出则必然遗漏）

**跨文件关联检查**：
- 若分批审查，必须在"跨模块路径"推演中，显式检查批次间的接口一致性
- 例如：第 1 批的核心逻辑文件与第 2 批的接口头文件之间的调用链路是否完整

## 0. 差异检查（git diff）

- [ ] 使用 `git diff` 查看本次全部变更，确认无计划外的文件修改
- [ ] 变更范围与 plan.md 中的"涉及文件"清单一致
- [ ] 删除的代码确实无残留引用（全局搜索确认）

## 1. Plan 对齐

- [ ] plan.md 中的每一步都在代码中有对应实现
- [ ] 没有私自修改 plan 中未提及的文件
- [ ] 没有遗漏 plan 中标记为"必须"的步骤
- [ ] 如有偏差，偏差是否经过用户确认或已在文档中记录
- [ ] **涉及文件对齐**：代码新增/修改的文件路径是否与 plan.md "涉及文件"清单一致，有无 plan 外的文件被修改（通过 `git diff --name-only` 核对）
- [ ] **设计约束对齐**：spec.md 中明确的设计约束（如 PIMPL、接口定义、数据格式）是否在代码中落实，有无未经记录的偏离

## 1.5 占位实现检测

- [ ] **无未实现的占位函数**：使用 `grep -R "Not implemented\|Not fully implemented\|TODO\|FIXME" src/` 扫描；任何与 spec 验收标准相关的占位都必须标记为 blocker
- [ ] **spec 验收标准对齐**：逐条检查 spec 中的验收标准，确认代码中已有对应实现路径，而非仅存在接口声明
- [ ] **端到端主流程可运行**：至少有一条测试或示例能走完从入口到输出的完整主流程（如 SDK 生成诊断包并写入文件）

## 2. Constitution 符合

- [ ] 新增文件放在正确的目录下
- [ ] 命名符合项目约定（PascalCase / camelCase / snake_case）
- [ ] 没有跨层调用（如前端组件直接访问数据库）
- [ ] 没有引入 plan 中未提及的新依赖
- [ ] 工具函数是否复用已有实现，而非重复造轮子

## 3. 逻辑正确

- [ ] 主流程输入输出符合 spec 的验收标准
- [ ] 空值处理：所有可能为 null/undefined 的参数都有防护
- [ ] 越界处理：数组索引、字符串操作、分页参数
- [ ] 错误分支：失败路径有处理，不是静默吞掉异常
- [ ] 并发安全：如有异步/多线程，是否存在竞态条件
- [ ] 副作用：函数是否产生了未声明的副作用
- [ ] **多入口一致性**：如果同一业务规则（如"某条件不满足时数据不参与计算"）在多个代码入口被使用（如 UI 的 DisplayRole/ForegroundRole、Model 的 InitData/状态判断、Exporter 的格式化），是否所有入口都遵循了同一前置判断逻辑
- [ ] **边界自测与断言**：关键业务逻辑（尤其是边界判断、区间处理）是否编写了内联断言测试（assert/Q_ASSERT 等），覆盖边界值、等价类分界点、异常输入。即使项目无正式测试框架，也应要求用断言验证核心逻辑
- [ ] **运行时连接完整性**：如果代码涉及运行时连接机制（信号、事件、回调、反射映射等），确认其声明-发射-绑定的完整链路无断链，中间转发节点无遗漏
- [ ] **多分支变量赋值一致性**：在 `if/else if` 或 `switch` 多个分支中，如果某个变量在所有分支后都被使用，确认每个分支都正确赋值
  - 例如：分支 A 赋值了 `oldName`，分支 B 是否也赋值了？遗漏会导致下游逻辑使用空值

## 7. C++ 项目专项（如适用）

### 封装与依赖隔离

- [ ] **PIMPL / 前向声明合规**：如果 spec/plan 明确要求 PIMPL（`struct Impl; std::unique_ptr<Impl>`），头文件中是否**完全不暴露**第三方库类型（即使是裸指针或前向声明也不应出现）
- [ ] **依赖倒置原则（DIP）**：高层模块（如 ModelManager）是否通过抽象接口或工厂函数创建低层实现，而非直接 `#include` 具体类的头文件并 `new` 具体类
- [ ] **第三方类型隔离**：头文件中是否包含第三方库的头文件（如 `llama.h`），或是否在头文件中暴露了第三方库的 struct/enum 类型（前向声明的裸指针也算暴露）
- [ ] **私有方法暴露**：头文件中是否暴露了本应在 `.cpp` 中实现的私有辅助方法（如 `BuildPrompt`、`GenerateResponse` 等），导致头文件膨胀

### C++ 基础安全

- [ ] **const 引用安全性**：未对 `std::priority_queue::top()`、`std::set::begin()` 等容器返回的 const 引用做 `const_cast` 并修改
- [ ] **迭代器失效**：在遍历容器时，未在循环体内做可能导致迭代器失效的操作（如 `vector::push_back`、`map::erase` 未使用返回的新迭代器）
- [ ] **空容器访问**：`front()` / `back()` / `top()` 调用前已确认容器非空
- [ ] **范围 for 与临时对象**：范围 for 循环的容器表达式不是临时对象（或临时对象生命周期足够覆盖整个循环）
- [ ] **回调线程安全**：回调函数的注册/注销与调用是否发生在不同线程？若是，是否有同步机制？
- [ ] **单例生命周期**：全局单例的析构是否晚于所有使用它的线程？是否存在析构后访问风险？
- [ ] **Windows Socket 清理**：每个 `WSAStartup` 都有对应的 `WSACleanup`，异常路径不遗漏
- [ ] **字符串转数值异常防护**：所有使用 `std::stoi`、`std::stoul`、`std::stof`、`std::stod` 的场景都有 `try/catch` 或前置正则校验，不会抛出未捕获异常导致崩溃
- [ ] **数据库 Schema 与数据结构一致性**：建表 SQL 中的列类型与程序中实际写入/读取的类型一致（特别注意 SQLite 弱类型可能掩盖 `INTEGER` vs `TEXT` 的不匹配）
- [ ] **旧数据库 Schema 升级**：表结构变更（新增列/改类型）时是否配套旧数据库迁移方案
  - 检查 `CREATE TABLE IF NOT EXISTS` 后是否有 `PRAGMA table_info()` + `ALTER TABLE ADD COLUMN`
  - 新增列是否有合理的 DEFAULT 值，避免旧数据行出现 NULL 异常
- [ ] **Qt SQL 线程安全**（如项目使用 Qt + SQLite）：
  - 搜索 `ThreadPool::push_task` / `QtConcurrent` / `QThread` lambda 中的数据库操作
  - 确认后台线程没有直接使用主线程创建的 `QSqlDatabase` 对象（`QSqlQuery query(m_db)`）
  - 搜索 `, true)` 在 `Update/Insert/Remove/Query` 中的使用，确认单条操作未误用 async
  - 后台线程如需数据库操作，是否创建了独立连接（`QSqlDatabase::addDatabase(..., connName)`）
- [ ] **Protobuf 字段访问一致性**：代码中引用的 protobuf 字段名、枚举值与 `.pb.h` 实际生成的一致（非基于记忆假设）

## 8. 场景推演

- [ ] **正常路径**：枚举 3-5 个核心业务的正常输入，推演代码的输出是否符合预期
- [ ] **异常路径**：枚举失败场景（空值、越界、网络断开、文件不存在），推演错误处理是否正确
- [ ] **时序路径**：如果涉及状态机/标志位，推演多次调用、并发触发时的状态转换是否正确
- [ ] **跨模块路径**：如果修改涉及模块间通信，推演通知/回调的完整调用链是否正确
- [ ] **运行时连接触发路径**：对于新增的运行时连接，推演从声明到发射到绑定的完整链路，确认中间无断链

## 4. 可维护性

- [ ] 命名是否见名知意（不看注释能猜到用途）
- [ ] 函数长度是否可控（超过 50 行需考虑拆分）
- [ ] 复杂度：是否引入不必要的抽象层
- [ ] 重复代码：是否有可提取的公共逻辑
- [ ] 注释：复杂算法是否有说明，废话注释是否已删除

## 5. 可验证性

- [ ] 关键路径是否有日志/埋点
- [ ] 纯函数是否易于单元测试
- [ ] 有副作用的代码是否可观测（输入什么、输出什么、改了什么状态）
- [ ] 验收标准中的检查项是否能通过代码行为验证

## 6. 编译与构建检查

- [ ] 代码是否能在项目现有构建系统中编译通过（不引入计划外的构建文件修改）
- [ ] 新增的源文件是否已被构建系统正确收集（检查 GLOB/GLOB_RECURSE、CMakeLists.txt 等）
- [ ] 新增的依赖库是否已正确链接
- [ ] 是否避免了硬编码源文件路径到构建配置文件中（优先使用项目已有的抽象机制）

### 6.1 运行时验证（GUI / 可视化项目强制）

**原则：编译通过 ≠ 运行正确。对于 GUI、可视化、游戏渲染类项目，必须在审查前做基本运行验证。**

- [ ] **启动无崩溃**：程序能正常启动，不闪退、不卡死
- [ ] **核心 UI 渲染正常**：主窗口/画布/场景能正确显示，无黑屏、无空白、无错位
- [ ] **中文/国际化文本正确**：涉及非 ASCII 字符的项目，运行后检查文字是否乱码
- [ ] **基本交互可用**：按钮点击、输入框输入、鼠标悬停等基础交互是否响应
- [ ] **坐标/布局合理**：元素位置是否在设计预期范围内，无严重偏移或重叠

> **为什么重要**：GUI 项目的很多 bug（sceneRect 未初始化、Z-order 错误、编码不匹配）在编译阶段完全无法暴露。如果审查前未运行验证，这些 bug 会直接流到用户手里。

## 评分速查

| 发现的问题数 | 单项得分参考 |
|-------------|-------------|
| 0 个问题 | 9-10 分 |
| 1-2 个 minor 问题 | 7-8 分 |
| 1 个 major 问题 或 3+ minor | 5-6 分 |
| 2+ 个 major 问题 或 逻辑错误 | < 5 分 |

**major 问题定义**：可能导致生产故障、数据丢失、安全漏洞、或严重违背设计文档。
**minor 问题定义**：影响可读性、可维护性、或存在优化空间，但不会直接造成故障。
