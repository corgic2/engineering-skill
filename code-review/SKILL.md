# Code Review

## 核心原则

**设计 90 分，代码 60 分，最终交付就是 60 分。**

方案再漂亮，执行层出问题（边界没处理、变量名冲突、漏了异常分支）都会直接拉低交付质量。代码审查是方案质量落地的最后一道闸。

### 功能错误绝对阻塞原则

**任何导致业务逻辑与需求不符、或同一业务规则在不同代码入口处理不一致的代码问题，无论其他维度评分多高，都必须列为阻塞问题（blocker），综合评分必须降到有条件通过（< 8.0）区间。**

功能错误不能降级为"建议项"。评分诚实不是给自己放水，而是对交付质量负责。

**功能错误的典型特征**：
- 业务逻辑与需求/验收标准不符（如"光功率异常时不参与计算"但代码中某些入口仍参与计算）
- 同一前置条件在 DisplayRole 中处理了，但在 ForegroundRole/InitData/Export 中未处理
- 边界条件处理与 spec 明确约定的范围不一致
- 计算逻辑错误导致数据结果不正确
- spec 明确要求的功能在代码中仍为空实现、stub 或仅返回占位错误码
- 验收标准中列出的端到端路径无法通过现有代码实际运行

**非功能错误（可列为建议项）**：
- 命名不规范、注释缺失
- 代码重复、可提取公共函数
- 缺少防护性校验（如参数范围检查）—— 注意：如果 spec/plan 明确要求了该校验，则属于功能错误
- 性能优化空间

## 审查流程

```
代码产出
    ↓
[1] 差异检查（git diff）←── 使用 git diff 查看所有变更，确保无计划外的修改
    ↓
[2] 对齐检查          ←── 代码是否实现了 plan.md 的全部步骤
    ↓
[2.5] 占位实现检测    ←── 扫描代码中的 stub / TODO / "Not implemented"，并对照 spec 验收标准检查
    ↓
[3] 架构符合性检查    ←── 是否违背 constitution.md 的约束
    ↓
[4] 逻辑与边界检查    ←── 主逻辑正确 + 异常分支覆盖
    ↓
[5] 场景推演          ←── 枚举关键业务场景的输入/输出，验证修改后行为是否符合预期
    ↓
[6] 代码质量检查      ←── 可读性、重复度、依赖引入
    ↓
[7] 模型自评（五维）
       ↓ 综合评分 < 8.0 或有功能错误
       └──→ 标记问题 → 打回修复（优先）或标记风险（次要）
       ↓ 综合评分 ≥ 8.0 且无功能错误
[🛑 输出审查报告]
       ↓ 用户确认
[验收通过 / 继续修复]
```

## 五维审查评分

每项满分 10 分，综合评分 = 五项平均分。

| 维度 | 检查要点 | 典型不通过项 |
|------|----------|-------------|
| **Plan 对齐** (10分) | 是否完整实现了 plan.md 的所有步骤；有无遗漏或擅自增加未设计的改动 | 跳过了 plan 中的某一步；私自改了没设计的文件 |
| **Constitution 符合** (10分) | 是否遵循项目架构约束（目录结构、命名规则、模块边界） | 组件放在错误目录；命名不符合约定；越层调用；违反依赖倒置（高层模块直接依赖低层实现） |
| **逻辑正确** (10分) | 主流程是否正确；边界条件（空值、越界、空集合）是否处理；并发/时序是否安全；封装边界是否被破坏（内部实现意外暴露给外部） | 空指针风险；数组越界；缺少错误分支；内部类型/实现暴露在公开 API 中；**spec 要求的 PIMPL 未落实（头文件暴露第三方库裸指针）**；**GetEngine() 返回悬空裸指针** |
| **可维护性** (10分) | 可读性（命名、注释、复杂度）；重复代码；引入的不必要依赖 | 三层抽象包一层函数；重复工具方法散在多处；引入用不到的库 |
| **可验证性** (10分) | 是否容易测试；**代码是否能在项目现有构建系统中编译通过**；关键路径是否有日志/埋点；是否方便验收标准检查 | 缺少编译验证；破坏了项目原有构建抽象（如硬编码源文件路径到构建系统配置）；纯副作用函数无法断言；缺少关键日志；状态不可观测 |

**评级与动作**：
- 🏆 **≥ 8.0 且无功能错误**：通过。输出审查报告，标记 1-2 个建议项即可。
- ⚠️ **5.0 - 7.9 或 ≥ 8.0 但有功能错误**：有条件通过。必须列出阻塞问题（blocker）和建议项（suggestion）。
  - 若阻塞问题中包含**功能错误**：必须回到 **spec-driven-dev 阶段 1（需求澄清）或阶段 2（方案设计）**，重新确认需求边界，更新 plan/tasks，然后重新执行 → 编译 → 审查。
  - 若阻塞问题仅为架构违规/代码质量问题：回到 **[spec-driven-agent]** 修正代码 → 重新触发本 Skill 审查。
- ❌ **< 5.0**：不通过。必须打回修复，禁止直接验收。

## 审查报告格式

```markdown
## 代码审查报告

### 评分

| 维度 | 得分 | 说明 |
|------|------|------|
| Plan 对齐 | X/10 | ... |
| Constitution 符合 | X/10 | ... |
| 逻辑正确 | X/10 | ... |
| 可维护性 | X/10 | ... |
| 可验证性 | X/10 | ... |

**综合评分：X.X / 10**

### 阻塞问题 — 功能错误（必须修复，不能降级）
- [ ] <问题 1：具体文件和行号/位置，说明为什么属于功能错误>
- [ ] <问题 2：...>

### 阻塞问题 — 架构/质量违规（必须修复）
- [ ] <问题 1：具体文件和行号/位置>
- [ ] <问题 2：...>

### 建议项（可选优化，非阻塞）
- [ ] <建议 1>
- [ ] <建议 2>

### 审查错误追踪记录
```yaml
workflow-state.md 更新:
  review:
    passed: false
    blockers:
      - "问题描述摘要"
    fix-verified:  # 修复后填写
      - blocker: "问题描述"
        fixed-in: "commit/文件"
        re-reviewed: true
```

### 与设计文档的偏差
- plan.md 步骤 X 要求 <...>，实际代码 <...>，偏差原因：...

### 验收意见
- [ ] 通过，无需修改
- [ ] 有条件通过，建议项可选修
- [ ] 不通过，需修复阻塞问题后重新审查
```

## 关键规则

- **审查必须对照 plan.md 和 constitution.md**。没有设计文档的代码审查是盲人摸象。
- **阻塞问题必须具体**：给出文件路径、函数名、具体问题，禁止泛泛而谈"代码有点乱"。
- **不要替代码做假设**：如果某段代码的意图不清楚，标记为"意图不明，需确认"。
- **评分诚实**：不要因为是自己写的代码就放水。已知缺陷必须扣分。
- **审查错误必须追踪**：所有功能错误必须在 `workflow-state.md` 的 `review.blockers` 中记录；修复后必须重新编译验证和代码审查，确保同一错误不再出现。

## 连接指南：下一步该触发谁

本 Skill 的输出是**审查报告**。根据评分结果：

- **综合评分 ≥ 8.0 且无功能错误**：通过，可进入验收。用户确认后：
  - **→ [execution-retrospective]**：如用户要求复盘（"为什么会出现这个 bug""下次怎么避免"）
  - **→ 结束**：如无需复盘

- **综合评分 5.0 - 7.9，或 ≥ 8.0 但有功能错误**：有条件通过。列出阻塞问题，由用户决定：
  - **阻塞问题含功能错误** → 回到 **[spec-driven-dev] 阶段 1/2**，对遗留 bug 重新进行需求澄清/方案设计，更新 plan/tasks（已完成的 task 标记为 done，新增 bug 修复 task），然后重新执行 → 编译 → 审查
  - **阻塞问题仅为架构/质量违规** → 回到 **[spec-driven-agent]** 修正代码 → 重新触发本 Skill 审查
  - 标记风险继续 → 记录风险后进入验收（不推荐，需用户明确承担风险）

- **综合评分 < 5.0**：不通过。必须：
  - **→ [spec-driven-dev] 阶段 1/2**：重新澄清需求或设计方案

### 审查与 SDD 的衔接规则

- 阻塞问题必须关联到 plan.md 的具体步骤（"plan 第 3 步要求做 X，代码实际做了 Y"）
- 如发现 constitution.md 的约束被违反，在审查报告中标记并建议更新 constitution
