# Execution Retrospective

## 核心原则

**留痕不是为了追责，是为了让系统下次不再犯同样的错。**

复盘的价值不在写一份漂亮的报告，而在把一次执行的偏差转化为 Skill 的改进。如果复盘后 Skills 没有变化，这次复盘就是浪费时间。

## 复盘输入

开始复盘前，必须收集以下材料（如缺失，先要求用户补充）：

1. **requirement-clarifier** 产出：需求确认单
2. **spec-driven-agent** 产出：spec.md + plan.md + tasks.md + 执行记录
3. **code-review** 产出：审查报告（如有）
4. **用户反馈**：验收意见、生产故障报告、测试反馈

## 五维复盘框架

逐层回溯，定位失效点：

| 维度 | 核心问题 | 检查 Skills 哪里失效 |
|------|---------|---------------------|
| **需求** | 是不是理解错了需求？ | requirement-clarifier 是否遗漏了隐含需求或关键约束？ |
| **设计** | spec/plan 是否完备？ | spec-driven-agent 的自评是否放水？验收标准是否模糊？ |
| **执行** | 代码是否符合设计？ | 执行阶段是否擅自发挥了 plan 之外的内容？ |
| **审查** | 为什么审查没拦住？ | code-review 的检查清单是否遗漏了这类问题？评分是否虚高？ |
| **流程** | 哪一步的 check 失效了？ | 是否有该触发某 Skill 却未触发的情况？ |

## 根因分类与改进映射

定位根因后，按以下规则输出改进动作：

| 根因类型 | 典型表现 | 改进目标 Skill | 改进动作 |
|----------|---------|---------------|----------|
| 需求漏问 | 用户说"我以为你知道要兼容旧数据" | requirement-clarifier | 在 clarification-template.md 补充追问项 |
| 需求误判 | 把解决方案当需求（"加 Redis"→实际要缓存） | requirement-clarifier | 在 SKILL.md 中强化"用户给的是方案不是需求"的案例 |
| 设计遗漏 | plan 没考虑并发/回退/旧数据迁移 | spec-driven-agent | 在自评维度中提高"边界完整"的权重，或在 plan.md 模板中增加"回退方案"栏目 |
| 自评放水 | 明明有漏洞，模型给自己打 9 分 | spec-driven-agent | 在 SKILL.md 中补充该漏洞类型的典型扣分示例 |
| 执行偏离 | 代码改了 plan 之外的文件 | spec-driven-agent | 在 tasks.md 模板中强化"涉及文件"的对齐检查 |
| 审查遗漏 | 空指针/越界没被发现 | code-review | 在 review-checklist.md 补充对应检查项 |
| 审查虚高 | 有明显问题仍给 8 分 | code-review | 在 SKILL.md 评分参考中补充该类问题的典型得分 |
| 流程跳过 | 没走澄清直接写代码 | spec-driven-agent | 在连接指南中强化"需求不清时必须触发 requirement-clarifier" |
| constitution 失效 | 代码违背架构约束但没被发现 | code-review | 在 review-checklist.md 的 Constitution 检查中增加具体规则 |
| 重复踩坑 | 同类 bug 出现 2 次以上 | constitution.md（项目级）| 在项目 constitution.md 中新增红线规则 |
| Skill 文档分层混乱 | 原则章节塞满代码示例、命令参数、完整模板 | 目标 Skill | 将细节抽离到 references/，原则章节只留高阶指导和引用 |

## 双输出格式

每次复盘必须产出两份文档：

### 1. retrospective.md —— 本次复盘报告

```markdown
# Retrospective: <一句话总结>

## 执行概况
- **原始需求/反馈**: <...>
- **最终产出**: <...>
- **用户反馈**: <验收通过 / 发现 bug / 需要返工>

## 五维回溯

### 需求
- **问题**: <有无理解偏差？>
- **证据**: <需求确认单第 X 条 vs 实际反馈>
- **根因**: <漏问 / 误判 / 假设未确认>

### 设计
- **问题**: <spec/plan 是否覆盖了该场景？>
- **证据**: <plan.md 第 X 步>
- **根因**: <遗漏 / 过于乐观 / 验收标准模糊>

### 执行
- **问题**: <代码是否按 plan 实现？>
- **证据**: <代码位置 vs plan 步骤>
- **根因**: <擅自发挥 / 理解偏差 / 技术债>

### 审查
- **问题**: <为什么没发现？>
- **证据**: <审查报告评分 vs 实际问题>
- **根因**: <检查清单遗漏 / 评分放水 / 未对照 plan>

### 流程
- **问题**: <哪步 check 失效了？>
- **根因**: <跳过了某 Skill / 某门槛形同虚设>

## 根因总结
<用一句话概括核心根因：不是"代码有 bug"，而是"为什么 bug 流到了用户手里">

## 即时改进（本次就执行）
- [ ] <具体动作 1>
- [ ] <具体动作 2>
```

### 2. skill-evolution-patch.md —— Skill 改进指令

这是本 Skill 的核心产出。必须给出**可直接执行的修改指令**，而非泛泛建议。

```markdown
# Skill Evolution Patch

## 改进项 1: <目标 Skill 名称>

**问题**: <一句话描述>
**根因**: <来自 retrospective 的哪一维>

**修改指令**:
- **文件**: `<skill-name>/SKILL.md` 或 `<skill-name>/references/<file>.md`
- **位置**: <具体章节或模板>
- **动作**: <add / modify / delete>
- **内容**:
  ```
  <具体的添加或修改内容，直接可粘贴>
  ```

## 改进项 2: ...
```

**执行规则**：
- 如果改进项是补充检查清单、模板或案例，直接输出完整新增内容
- 如果改进项是修改评分标准或流程，输出新旧对比
- 如果改进项是在项目级 constitution.md 中新增红线，输出 constitution 补丁
- **禁止输出模糊建议**（如"建议多注意边界"），必须输出可落地的文本补丁

## 自进化执行原则

复盘的价值不在报告，而在 Skill 的进化。复盘完成后必须将改进落实到 Skill 文件的实际变更。

核心原则：
- **变更优先于报告**：改进必须落到 Skill 文件上，而非仅停留在复盘文档中
- **留痕优于记忆**：偏差和根因必须固化为检查清单或流程规则，而非依赖人脑记忆
- **闭环优于开环**：修改后的 Skill 必须在下一次同类场景中自动生效，形成进化飞轮

> **关键**：复盘不结束于报告，结束于 Skill 文件的实际变更。

## 何时必须复盘

不是每次执行都要复盘。以下情况强制复盘：
- 代码审查评分 < 8.0（说明流程某处失效）
- 用户验收后发现新问题（bug 流到了用户手里）
- 同一类问题 2 次以上重复出现
- 用户主动要求复盘

以下情况可跳过复盘：
- 一次通过，审查 ≥ 8.0，用户验收无异议，且无明显可沉淀的新模式

## 连接指南

本 Skill 是工作流的**终点**，也是**下一轮工作流的起点**。

- **入口**：来自 **[code-review]**（审查后）或用户主动提出复盘
- **出口**：执行 skill-evolution-patch 后，本轮结束。下一轮同类需求自动受益于改进后的 Skills

### 进化飞轮

```
执行 → 偏差 → 复盘 → 改进 Skills → 下一次执行更可靠 → 更少的偏差
```
