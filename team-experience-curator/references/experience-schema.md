# 经验条目结构（Experience Schema）

## 目录

- 字段定义
- 条目模板
- 正反例
- 可审计说明格式

## 字段定义

每条经验必须包含以下字段：

| 字段 | 含义 | 约束 |
|---|---|---|
| `title` | 一句话标题 | 陈述一个具体技术事实或约束，不是动作口号 |
| `when` | 适用场景 | **禁止泛化**。写清楚什么任务/什么条件下才适用，让召回方能判断"现在是否命中" |
| `what` | 建议 | 最具体、最安全、可执行的建议。能写出命令/类名/参数级别就写到那个级别 |
| `why` | 机制原理 | 为什么会这样，底层机制是什么。没有 why 的经验无法被迁移到相似场景 |
| `scope` | 作用域 | 项目级 / 模块级 / 文件级 |
| `component` | 所属组件 | 模块、子系统或目录名 |
| `source` | 对话证据 | 可引用到具体轮次的证据：用户原话、报错、验证结果 |

## 条目模板

```markdown
### <title>

- **When**: <什么场景下适用，越具体越好>
- **What**: <最具体、最安全、可执行的建议>
- **Why**: <机制原理>
- **Scope**: <项目级 | 模块级 | 文件级>
- **Component**: <模块/子系统名>
- **Source**: <第 N 轮用户原话/报错/验证结果摘要>
- **存疑**: <仅当事实校验无法完成时存在，说明无法验证的原因>
```

## 正反例

### 正例：陈述隐藏技术事实

```markdown
### 订单服务的重试必须由调用方显式开启，框架默认不重试

- **When**: 在 order-service 中通过 RpcClient 调用下游接口，需要考虑失败重试时
- **What**: 在调用点显式传 `RetryPolicy.fixed(3, 200ms)`；不要依赖框架默认行为
- **Why**: 框架默认 `RetryPolicy.NONE`，因为历史上有下游接口非幂等导致重复扣款，
  架构组随后把默认值改为不重试，重试策略下放到各调用方按幂等性自行决定
- **Scope**: 模块级
- **Component**: order-service / rpc
- **Source**: 第 12 轮用户："这里不能靠框架默认重试，默认值是 NONE，
  上次重复扣款事故后改的"；第 15 轮 grep 确认 `RpcClient` 默认参数为 `RetryPolicy.NONE`
```

为什么合格：命中**逻辑镜头**（默认行为反直觉，读代码注释都不一定能发现背后的事故原因），
有证据（用户原话 + 代码检索验证），When 具体，What 可执行，Why 解释了机制。

### 反例：操作清单（是文档不是经验）

```markdown
### 修改重试配置的步骤

- **When**: 需要改重试配置时
- **What**: 1. 打开 config/rpc.yaml；2. 找到 retry 字段；3. 改成 3；4. 重启服务
- **Why**: 要改重试次数
- **Scope**: 文件级
- **Component**: rpc
- **Source**: 第 10 轮
```

为什么不合格：只罗列"去哪里改什么"，没有任何**不容易直接发现**的信息——
这些步骤读一遍配置文件就能自己推出来。三镜头都不命中，召回后不会让 Agent
产生正向行为变更。这类内容属于项目文档，不进经验库。

## 可审计说明格式

每条经验写入经验库时，同时（在写入汇报中，或作为条目 HTML 注释 `<!-- audit: ... -->`）输出审计说明：

1. **为什么这是经验**：命中了哪个镜头（黑话/索引/逻辑），满足哪些合格条件；
2. **通过了哪些垃圾检查**：九类垃圾特征逐项确认不命中（或重点说明容易被误判的几类）；
3. **证据来自哪几轮对话**：列出轮次与对应内容摘要；
4. **事实校验结果**：检索了什么、结论是什么（通过 / 存疑及原因）。
