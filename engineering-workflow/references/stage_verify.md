# 阶段：构建验证与运行验证

## 目标

从"改完代码"到"敢说完成"，全部用文件证明，不靠 AI 自报。

## 构建验证

使用 `AIRunWorkDocs/tools/build_verify.sh`：

```bash
./AIRunWorkDocs/tools/build_verify.sh
```

成功判据：

1. 退出码 0。
2. `build/build_report.txt` 存在且包含 `BUILD_PASS`。
3. `build/.build_sentinel` 文件更新时间晚于源码改动时间。

构建错误分类：

| 类别 | 示例 | 处理 |
|------|------|------|
| A 可自修复 | 语法错误、标识符未声明、类型不匹配、依赖缺失 | AI 直接修，重跑构建，≤3 轮 |
| B 需用户介入 | 构建配置错、环境缺失、第三方库问题、错误不在改动集合 | 立即停下报告用户 |

## 运行验证

根据项目类型执行：

- **GUI/可视化**：程序正常启动，核心画面渲染正确，无乱码，基本交互响应。
- **Web/API**：服务启动，关键接口返回 200/预期 JSON，日志无 ERROR。
- **CLI/工具**：命令正常执行，输出符合预期，退出码正确。
- **库/SDK**：单测通过，示例代码可运行。

涉及 UI 改动时，按 `ui_mapping.md` 核对数值。

## 验证闭环五道关

1. `build_report.txt` 退出码 0。
2. 测试用例通过（单元/集成）。
3. 运行日志命中关键路径。
4. 产物截图/转储/响应符合预期。
5. `result.md` 状态字段为 `PASS`（唯一判据）。

## 失败处理

- A 类问题：阶段内重试 ≤3 轮，超过则升级为 B 类。
- B 类问题：停下，报告用户，不回退代码但记录到 `timeline.txt`。
