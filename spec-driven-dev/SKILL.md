# Spec-Driven Dev — 开发任务统一入口

## 开发者视角判断规则

**第一原则：任何可能改变文件内容的操作，都是开发任务，必须走完整流程。**

收到用户请求时，先判断：

```
用户请求
    ↓
是否涉及以下任一？
  - 创建/修改/删除代码文件
  - 编写新功能、修复 bug、重构代码
  - 修改配置文件、脚本、文档（当文档是系统一部分时）
  - 运行可能改变文件状态的命令（如格式化、生成代码）
    ↓ 是
强制进入 SDD 完整流程
    ↓ 否
正常对话处理（分析、咨询、读取但不修改）
```

**典型判断示例**：

| 用户说的话 | 是否开发任务 | 理由 |
|-----------|-------------|------|
| "帮我修一下搜索分页的 bug" | ✅ 是 | 涉及代码修改 |
| "看看这个文件里有什么" | ❌ 否 | 只读，不涉及变更 |
| "分析一下这段代码的问题" | ❌ 否 | 只分析，不修改（但如果用户随后说"那你修一下"，立即切换为开发任务） |
| "帮我写个登录接口" | ✅ 是 | 涉及代码创建 |
| "给我讲讲这个模块的设计" | ❌ 否 | 纯咨询 |
| "把这个函数重构一下" | ✅ 是 | 涉及代码修改 |

## 阶段路由：不走回头路，也不跳步

> **明确禁止进入仅制定计划不执行的 plan 模式。触发本 Skill 后，必须严格按照以下 SDD 完整流程推进，涵盖设计、执行、验证、审查全阶段。**

开发任务一旦启动，必须按顺序经过以下阶段。**根据当前上下文判断处于哪个阶段，然后执行该阶段，禁止跳步。**

```
[阶段 0] 入口判断 → [阶段 1] 需求澄清 → [阶段 2] 方案设计
    → [阶段 3] 用户确认 → [阶段 4] 代码执行
    → [阶段 5] 执行后预自检 → [阶段 6] 代码审查
    → [阶段 7] 编译与运行验证 → [阶段 8] 验收/复盘
```

### 如何判断当前处于哪个阶段？

**每次启动开发任务时，先执行阶段 0 入口判断，然后执行以下检查（不可跳过）**：

1. 判断用户请求是否涉及文件变更、代码编写/修改、配置调整等开发任务（详见上方「开发者视角判断规则」）。若是纯咨询，走旁路路由，不进入 SDD 流程
2. 检查当前项目目录是否存在 `Agentic/sdd/*/workflow-state.md`（每个需求一个子目录）；如项目未使用 `Agentic` 目录，则查找 `sdd/*/workflow-state.md`
3. 如果存在，读取 `stage` 字段，从该阶段继续
4. 如果不存在，在 `Agentic/sdd/<需求名称>/`（或项目约定的 `sdd/<需求名称>/`）下创建新的 workflow-state.md，stage 设为 "requirement-clarification"，从阶段 1 开始
5. 向用户汇报当前阶段："检测到进行中的任务 [xxx]，当前处于 [阶段名]，是否继续？"

然后检查当前对话上下文和文件系统中是否存在以下产物：

| 检查项 | 如果存在 | 说明当前阶段 |
|--------|---------|-------------|
| 需求确认单 + 用户已确认 | 是 | ≥ 阶段 2，可以开始设计 |
| spec.md + plan.md + tasks.md + 自评 ≥8.0 | 是 | ≥ 阶段 3，等待用户确认 |
| 用户明确说"确认执行"/"可以动手" | 是 | ≥ 阶段 4，可以执行代码 |
| 代码已执行，有产出文件 | 是 | ≥ 阶段 5，执行执行后预自检 |
| 执行后预自检通过（workflow-state.md 中 `pre_review_passed: true`） | 是 | ≥ 阶段 6，执行代码审查 |
| code-review 报告 ≥8.0 且无功能错误 | 是 | ≥ 阶段 7，进行编译与运行验证 |
| 编译与运行验证完成（编译通过或用户明确跳过） | 是 | ≥ 阶段 8，等待用户验收 |
| 用户反馈"复盘一下" | 是 | 当前在阶段 8 → 触发复盘；不在阶段 8 → 视为对当前阶段的反馈或新任务，按当前阶段规则处理 |

**阶段判定优先级**：从上到下依次检查。先找到的最高阶段就是当前阶段。

### 各阶段执行规则

#### 阶段 1：需求澄清（强制）

**触发条件**：
- 刚收到开发任务，还没有需求确认单
- 或者用户补充了新信息，需求发生变化

**执行**：
- 调用 requirement-clarifier 的工作方式，输出需求确认单
- 如果需求非常明确（用户直接给了具体输入/输出/边界），可以简化确认单，但必须落到纸上让用户点头
- **禁止在需求未确认时直接进入设计**

**输出方式（禁止 ask 对话模式）**：
- 直接输出结构化的需求确认单，禁止使用 `AskUserQuestion` 开启多轮碎片化追问
- 如需补充信息，在确认单的"待确认问题"中一次性列出，等待用户集中回复
- 不要在未获得用户确认的情况下进入下一阶段

**出口**：用户明确确认需求单（如"没问题，按这个做"、"确认"、"可以"）

##### 阶段 1 附加：编译与运行验证方式确认（强制）

**原则**：
> 编译与运行验证不是阶段 7 才临时决定的事项。必须在阶段 1 就明确提出，让用户确认，避免到阶段 7 才发现构建方式不明、环境缺失或用户不愿承担长时间构建成本。

**必须在阶段 1 确认的编译相关事项**：

| 确认项 | 说明 | 不确认的风险 |
|--------|------|-------------|
| **项目构建系统** | 使用何种构建系统（CMake / Makefile / build.sh / Maven / npm / 其他） | 阶段 7 无法确定正确编译入口 |
| **具体编译命令** | 完整的可执行命令（如 `make`、`cmake --build .`、`npm run build`） | 阶段 7 需要再次请示，阻塞交付 |
| **编译目标范围** | 全量构建 / 模块构建 / 单文件检查 | 验证范围与需求不匹配 |
| **预计构建时间** | 是否超过 5-10 分钟 | 用户可能不愿等待，导致阶段 7 被迫跳过 |
| **运行验证需求** | 是否需要在编译通过后运行程序（尤其是 GUI/可视化/游戏项目） | 验收标准不一致 |
| **跳过编译的条件** | 什么情况下可以跳过阶段 7（如环境未就绪、用户明确放弃） | 阶段 8 发现阻塞问题时责任不清 |
| **必要前置环境** | 是否需要预先安装依赖、配置环境变量、初始化子模块 | 阶段 7 因环境缺失失败 |

**阶段 1 编译确认话术模板**：

> "为确保阶段 7 编译与运行验证顺利进行，请在需求确认时一并确认以下编译相关信息：
> 1. 项目构建系统：[CMake / Makefile / ...]
> 2. 具体编译命令：`[具体命令]`
> 3. 预计构建时间：[短 / 中 / 长，约 X 分钟]
> 4. 是否需要运行验证：[是 / 否]
> 5. 是否允许跳过编译：[允许的条件 / 不允许]
> 请确认以上信息无误，我们再进入方案设计。"

**强制约束**：
- **阶段 1 未确认编译方法的，禁止进入阶段 2 写 spec/plan**
- 若用户在阶段 1 表示"编译方法后续再定"，必须明确记录为"编译方法待确认"，并在阶段 2 的 plan.md 中预留"编译方法确认"任务，在阶段 3 再次确认
- 阶段 1 确认的编译方法应在 `workflow-state.md` 的 `confirmed.compile_method` 中记录

#### 阶段 2：方案设计（强制）

**触发条件**：需求已确认，还没有 spec/plan/tasks

**执行**：
- 调用 spec-driven-agent 的设计阶段，产出 spec.md + plan.md + tasks.md
- 完成模型自评（五维评分 ≥8.0）
- **禁止在用户未审核方案前执行任何代码**

**输出方式（禁止纯 plan 模式）**：
- 方案设计是执行的前提，不是终点；自评达标后提交用户确认，等待"确认执行"类有效确认后再进入阶段 4
- 直接输出结构化的 spec / plan / tasks 摘要，禁止使用 `AskUserQuestion` 反复追问用户
- 所有待确认项应在方案摘要中结构化列出，避免进入只制定计划不执行的纯 plan 模式

**plan.md 必须包含"编译与运行验证方案"专章**：

在阶段 2 产出的 `plan.md` 中，必须单独设立"编译与运行验证方案"章节，内容至少包括：

1. **已确认的编译方法**：
   - 构建系统
   - 具体编译命令
   - 执行目录/环境要求
2. **验证范围**：
   - 编译哪些目标
   - 运行哪些测试
   - GUI/可视化项目需验证的画面/交互项
3. **超时与降级策略**：
   - 预计构建时长
   - 超过阈值时的处理方式
4. **编译失败处理原则**：
   - 是否允许在阶段 7 直接修补
   - 回退路径
5. **允许跳过编译的条件**（如用户明确放弃、环境缺失）

若阶段 1 未能确认编译方法，plan.md 中必须包含一个"Task 0：确认编译方法"，并在阶段 3 再次提请用户确认。

##### 阶段 2 内嵌入可视化设计（参考 mermaid-diagrams）

当方案涉及 3 个以上模块/类交互、数据流向、状态转换、时序交互、并发流程或重构对比时，应在 plan.md 中插入 Mermaid 图作为可视化补充。

**原则**：图是文字补充而非替代；须标注对应代码位置或 plan 步骤；复杂流程拆分多图。具体图表类型选择、语法规范、一致性检查清单参考 mermaid-diagrams Skill。

##### 阶段 2 内嵌入测试策略（参考 testing-strategy）

方案设计时须同步考虑可验证性：

- 每个涉及业务逻辑的 Task 必须伴随测试验证方案（单元/集成/边界/回归）
- 在 plan.md 或 tasks.md 中明确关键路径的测试覆盖要求
- 边界条件必须显式设计用例，禁止只测正常路径
- 测试产物（`test-cases.md`、`test-strategy.md`）放在 `Agentic/sdd/<需求名称>/` 下，与 spec/plan/tasks 同级
- 可执行测试代码按项目既有规范存放

**出口**：自评 ≥8.0，且用户明确确认方案（如"确认执行"、"动手吧"）

#### 阶段 2 附加检查：跨 Phase 技术债回溯

在产出新 Phase 的 plan.md 前，必须执行以下检查：

1. 检查当前项目是否存在 `Agentic/sdd/*/workflow-state.md`（或项目约定的 `sdd/*/workflow-state.md`）
2. 读取上一 Phase 的 workflow-state.md 中 `technical_debt` 字段
3. 检查项目根目录是否存在 `constitution.md`，读取其中的技术债清单
4. 在 plan.md 的"风险评估"章节中，明确列出：
   - 哪些技术债在本 Phase 修复（关联到具体 Task）
   - 哪些技术债延后处理（说明原因和计划修复 Phase）
5. 若技术债与本 Phase 新功能有耦合（如日志系统未接入影响本 Phase 的日志输出），必须在 plan 中标注依赖关系

**禁止**：不查阅上一阶段技术债就制定新 Phase 的 plan。

#### 阶段 3：用户确认（强制检查点）

这是不可跳过的 🛑 checkpoint。呈现完整方案给用户，必须得到明确确认。

**有效确认**："确认"、"没问题"、"执行吧"、"动手"、"可以"
**无效确认**："你先做"、"试试看"、"做好了给我看看" → 视为未确认，继续等待

**阶段 3 确认范围**：
- 方案本身的实现路径
- **阶段 1 已确认的编译方法（如有调整，需再次明确）**
- plan.md 中的"编译与运行验证方案"专章
- 允许跳过编译的条件

**强制等待机制**：如果用户回复不是有效确认列表中的任一表述，必须明确告知用户：
> "当前方案尚未确认，无法执行。请输入'确认'、'没问题'、'执行吧'、'动手'、'可以'之一，或提出修改意见。"

禁止在收到有效确认前以任何理由继续执行代码。

#### 阶段 4：代码执行（仅在确认后）

**触发条件**：用户已确认方案

**执行前自检（不可跳过）**：

在动手修改任何文件前，先对 tasks.md 执行一次内部自检。以下任一不满足，必须暂停执行，向用户说明问题并更新 plan/tasks：

| 检查项 | 通过标准 |
|--------|---------|
| **文件清单对齐** | tasks.md 中涉及的所有文件都在 plan.md 的"涉及文件"清单中，无计划外文件 |
| **依赖闭环** | 每个 task 的依赖链无循环，首个 task 的依赖为"无"或已存在于代码库中 |
| **完成标准可执行** | 每个 task 的"完成标准"都可以在当前环境下验证（如"编译通过"需确认编译命令已知） |
| **API/接口预演** | 若 task 涉及新增公开接口，已用伪代码验证签名可实现，无语言特性冲突 |
| **回退路径** | 若执行中发现 plan 有根本缺陷，已明确如何回退（如哪些文件可安全还原） |

**执行**：
- 按 tasks.md 逐步执行
- **每完成一个 task，立即更新 tasks.md**：将该 task 状态标记为 `done`，并填写执行记录（修改了哪些文件、验证结果）
- 如果 task 涉及的新增/删除文件与 plan 不一致，同步更新 plan.md 的文件清单
- 执行过程中如果发现 plan 有遗漏，必须停下来向用户说明，补充 plan 后再继续
- **禁止擅自修改 plan 之外的文件，禁止引入 plan 未提及的依赖**

##### 阶段 4 内的小步验证

阶段 4 不是「只写代码、最后一起验证」。在修改代码的过程中，应持续进行小步验证：

- **修改单个文件/模块后**：立即使用 plan 中已确认的编译命令进行编译或类型检查
- **修改接口定义后**：编译所有依赖该定义的目标模块
- **修改构建配置后**：重新配置构建系统并编译验证（构建配置变更应在 plan 中约定；若超出 plan，须暂停并告知用户）
- **禁止攒批**：除非是纯重构且已通过静态检查，否则不要攒多个文件后再一次性编译

小步验证属于阶段 4 的正常执行，阶段 3 的用户确认已包含对此类验证的授权，无需每次单独请示。验证结果必须记录到 task 执行记录中。

**出口**：所有 tasks 完成，且编码过程中的小步验证（如单文件编译、类型检查、lint、单元测试）无阻塞性问题。解释型语言项目的小步验证应至少包含 lint 和关键单元测试。

##### 编码原则：封装与扩展

代码执行时遵循以下原则，确保产出可维护、可演进：

**封装性（Encapsulation）**
- **单一职责**：一个函数/模块只做一件事，行长超过 40 行或嵌套超过 3 层时考虑拆分
- **最小暴露**：对外接口只暴露必要的行为，内部状态与实现细节隐藏
- **依赖显式化**：依赖通过参数/构造函数传入，避免全局状态、单例滥用、隐式耦合
- **边界清晰**：核心业务逻辑与基础设施（IO、网络、存储）分离，核心业务不直接依赖框架

**扩展性（Extensibility）**
- **开闭原则**：新增功能时优先「添加新代码」，而非「修改已有稳定代码」
- **条件收敛**：当同一处出现 3 个以上分支判断未来可能增长时，使用策略表/策略类/插件机制替代 `if/else` 或 `switch`
- **配置优于硬编码**：魔法数字、环境差异、可变规则提取到配置层，但配置项要有合理默认值
- **预留扩展点**：在模块边界处预留接口，但只实现当前需要的具体实现

**不过度设计（YAGNI）**
- **禁止为未来假设的需求写抽象层**：如果当前只有一种实现，不要强行提取接口/抽象基类
- **延迟抽象**：当同一模式出现第 3 次重复时，再考虑抽象成公共模块；第 2 次重复允许适度内联
- **三层规则**：抽象嵌套不超过 3 层（接口 → 抽象实现 → 具体实现），超过即视为过度设计
- **避免过早优化**：先让代码正确、可读，再考虑性能；性能瓶颈应通过 profiling 定位，而非预判
- **拒绝万能框架**：不引入重量级框架来解决简单问题，优先使用标准库和轻量依赖

**运行时依赖显式化**
- 运行时连接（信号、事件、回调等）在编译阶段不可见，必须通过代码结构或注释显式标注其存在
- 新增运行时连接时，必须确认声明-发射-绑定的完整链路

**代码组织建议**
- 按「功能/领域」组织目录，而非按「类型」（如 `controllers/` `models/`）
- 公共逻辑下沉到 `shared/` 或 `common/`，业务逻辑上浮到领域模块
- 测试与源码同目录或近邻放置，降低维护门槛
- 每个模块暴露一个清晰的入口（`index.js` / `__init__.py` / `mod.rs`），内部结构对外透明

##### 代码修改与重构的额外约束

按 tasks.md 执行具体代码修改和重构时，除上述通用编码原则外，还须遵守以下约束：

**封装性与复用性**
- **封装必须服务于复用**：提取公共函数/模块前，先确认它将在至少 2 个以上场景被复用；只为形式统一而封装的代码应回退为内联
- **最小且稳定的接口**：封装后的对外接口应尽可能小、语义清晰，避免把内部状态或临时实现细节暴露给调用方
- **复用效果可验证**：封装完成后，检查调用方是否确实因为封装而减少了重复代码或降低了耦合；如果反而增加复杂度，应撤销封装

**删除风险评估（重构删除）**
- **删除前必须评估**：删除任何既有代码（函数、类、文件、配置项）前，先自主完成以下检查：
  1. 搜索项目内是否仍有引用（文本搜索 + 编译/类型检查）。此类编译/类型检查属于阶段 4 小步验证的一部分，使用 plan 中已确认的编译命令，无需重复请示
  2. 判断是否破坏公开 API 或向后兼容
  3. 判断是否影响运行时连接（信号、回调、事件、插件加载点等）
  4. 判断是否影响测试、文档、脚本或构建流程
- **低风险方可删除**：只有在确认无外部引用、无兼容性风险、无运行时隐式依赖时，才能直接删除
- **高风险需留痕**：若删除可能造成影响但 plan 中已约定，应先在 plan.md/tasks.md 中记录删除理由、影响范围与回退方案；若 plan 未约定，必须暂停执行并向用户说明

**架构一致性**
- **符合既有架构**：新增代码的组织方式、抽象层次、命名风格、错误处理模式应与项目现有代码保持一致
- **不引入冲突模式**：除非 plan 中明确约定架构演进，否则不应在局部引入与全局架构冲突的新框架、新分层或新设计模式
- **优先复用现有抽象**：在添加新接口或新模块前，先检查项目是否已有可复用的抽象；存在时优先扩展现有抽象，而非创建平行结构

#### 阶段 7：编译与运行验证（强制）

**触发条件**：阶段 6 代码审查通过（≥8.0 且无功能错误）

**原则**：
> 阶段 7 是阶段 4 小步验证和阶段 6 代码审查之后的**最终集成验证**。代码审查已通过意味着逻辑和架构问题已收敛；阶段 7 使用 plan 中约定的命令执行整体编译（及测试），向用户交付最终结果。

**执行标准**：
- 使用 plan 中约定的编译命令执行整体构建
- 如编译失败，修复错误直至通过
- 如项目有测试入口，运行测试验证基本功能
- 如阶段 4 中已修改构建配置，阶段 7 须验证整体构建流程仍正确

**执行**：
- **编译授权**：阶段 3 用户确认方案（"确认执行"类表述）即视为已授权阶段 4 和阶段 7 的编译/类型检查。**但以下情况必须在阶段 7 最终编译前再次获得用户明确授权，否则禁止执行编译**：
  - 编译命令/构建方式**未在阶段 1 或阶段 2/3 中确认**
  - 预计构建时间较长（如 C++ 全量构建通常超过 5-10 分钟）
  - 用户此前明确跳过编译验证，修复后又需重新编译
  - 用户要求变更 plan 中约定的编译命令
  - 编译环境/依赖与阶段 1 确认时不一致
  - 编译命令涉及可能改变系统状态的副作用（如全局安装、清理其他目录、执行脚本）
  请示模板：
  > "代码已修改完毕，现在执行阶段 7 编译与运行验证。编译命令为：`[具体命令]`，预计耗时约 [X] 分钟。该命令已在阶段 1/3 确认 / 该命令尚未确认。是否执行？"
  用户说"执行"、"编译"、"可以" → 执行编译；用户说"不编译"、"跳过"、"晚点再说" → 记录为跳过；用户要求修改命令 → 更新 plan 后再次请示。
- **编译方法确认**：如果 plan 中未确认编译方式，**必须停止阶段 7**，回到阶段 1/2 补充确认，禁止在阶段 7 临时决定编译命令：
  - 项目构建系统（CMake / Makefile / build.sh / 其他）
  - 具体编译命令
  - 执行目录与前置环境
  - 是否有已有的模块/库导入抽象
  - 新代码是否需要集成到现有构建流程
- **编译前强制检查清单**（阶段 7 执行编译前必须逐项确认）：
  - [ ] 编译命令已在阶段 1 或阶段 3 获得用户确认
  - [ ] 当前工作目录正确，执行目录与确认时一致
  - [ ] 必要依赖/环境变量已就绪（与阶段 1 确认一致）
  - [ ] 编译命令不会破坏用户数据或执行计划外副作用
  - [ ] 已评估构建时长，必要时已向用户说明
  - [ ] 已明确编译失败后的回退路径
- **构建超时询问**：如果构建预计时间较长，在执行前必须询问用户："预计构建时间较长，是否继续执行编译验证？"
- 获得用户授权后，使用用户确认的编译命令尝试编译
- **编译失败后的回退路径**：任何在阶段 7 中为修复编译错误而修改代码的行为，都视为新的代码修改。修复后必须回到阶段 4 重新进行小步编译/类型检查验证，再经阶段 5 → 6 → 7，禁止在阶段 7 直接修补后跳过审查再次编译
- 编译通过后，如项目有测试入口，运行测试验证基本功能
- **边界自测（强制要求）**：对核心业务逻辑（尤其是边界判断、区间处理、状态转换），在源码中编写内联断言测试（如 C++ 的 `Q_ASSERT`/`assert`、其他语言的 `assert`），覆盖边界值、等价类分界点、异常输入。即使项目没有正式测试框架，也要用断言验证关键逻辑的正确性
- 对新增代码执行静态检查（lint / type-check / format-check），确保风格一致
- **编译未通过前，不得告知用户"做完了"**
- **运行时依赖不可见**：编译通过只验证了编译时和链接时依赖。运行时连接（信号、事件、回调等）在编译阶段不可见，需分两层验证：阶段 5 由执行者通过代码走查/场景推演确认链路完整；阶段 6 由审查者再次推演确认。

##### 运行验证（GUI / 可视化 / 游戏项目强制）

**编译通过后，对于涉及 UI 渲染、可视化、游戏画面的项目，必须执行运行验证：**

- [ ] 程序能正常启动，不闪退、不卡死
- [ ] 核心画面/画布/场景能正确渲染，无黑屏、无空白、无错位
- [ ] 涉及中文/国际化文本的项目，检查运行后文字是否乱码
- [ ] 基本交互（点击、输入、悬停）是否响应
- [ ] 元素坐标/布局是否在合理范围内

> **为什么强制**：GUI 项目的很多 bug（sceneRect 未初始化、Z-order 错误、编码不匹配、坐标转换偏差）在编译阶段完全无法暴露。阶段 7 的运行验证是把这些风险拦截在用户验收之前的最后一道闸。

**出口**：
- 编译通过 **且** 运行验证通过；或
- 用户明确放弃编译验证（标记为 `compiled: skipped`，仍须进入阶段 8 验收，但需明确告知用户风险）。

若阶段 7 被跳过，阶段 8 中凡发现需要修复的阻塞问题，修复后必须重新进入阶段 7 并再次获得编译授权。

**触发条件**：代码已执行完成

- [ ] **边界分支**：核心逻辑的所有 if/else、switch、错误码分支都已实现，非只写了主流程

#### 阶段 6：代码审查（强制，AI 自主完成）

**触发条件**：执行后预自检通过

**原则**：
> 代码审查放在编译验证之前，由 AI 自主完成，不占用用户注意力。审查通过后再进行编译/运行验证，最终只把编译/运行结果呈现给用户。

**执行**（参考并调用 code-review 方法论）：

阶段 6 是阶段 5 之后的深度审查，聚焦系统性问题，不再重复阶段 5 已完成的机械性自检：

1. **差异检查**：使用 `git diff`（或等效方式）查看所有变更，确认无计划外修改（阶段 5 已检查文件范围，阶段 6 在此基础上看变更内容的合理性）
2. **Plan 对齐检查**：从整体上验证 plan.md 的实现完整性，重点关注多步骤之间的衔接、依赖闭环、是否有 plan 外实现
3. **Constitution 符合性检查**：对照 constitution.md，确认目录结构、命名规则、模块边界、依赖方向等架构约束未被违反
4. **逻辑与边界深度检查**：主流程正确，异常分支覆盖，空值/越界/空集合/并发安全等边界已处理；评估是否与 spec 明确约定的范围一致
5. **场景推演**：枚举关键业务场景的输入/输出，验证修改后行为是否符合 spec/需求
6. **运行时依赖推演**：确认信号、事件、回调、插件加载点等的注册-触发-注销链路完整
7. **可验证性设计检查**：关键路径是否有测试/断言/日志覆盖；测试是否可独立运行、断言是否明确；是否方便验收标准检查。**本阶段不验证"能否编译通过"，编译结果由阶段 7 负责**
8. **代码质量深度检查**：可读性、重复度、命名一致性、依赖引入合理性、是否过度设计
9. **五维评分**：按以下五个维度评分

**阶段 6 五维评分定义（适配审查前置）**：

| 维度 | 检查要点 | 典型不通过项 |
|------|----------|-------------|
| **Plan 对齐** (10分) | 是否完整实现了 plan.md 的所有步骤；多步骤衔接是否正确；有无遗漏或擅自增加未设计的改动 | 跳过了 plan 中的某一步；私自改了没设计的文件 |
| **Constitution 符合** (10分) | 是否遵循项目架构约束（目录结构、命名规则、模块边界、依赖方向） | 组件放在错误目录；命名不符合约定；越层调用；违反依赖倒置 |
| **逻辑正确** (10分) | 主流程是否正确；边界条件是否处理；并发/时序是否安全；封装边界是否被破坏 | 空指针风险；数组越界；缺少错误分支；内部实现暴露在公开 API 中；spec 要求的 PIMPL 未落实 |
| **可维护性** (10分) | 可读性（命名、注释、复杂度）；重复代码；引入的不必要依赖；是否过度设计 | 三层抽象包一层函数；重复工具方法散在多处；引入用不到的库 |
| **可验证性设计** (10分) | 关键路径是否有测试/断言/日志覆盖；测试是否可独立运行；断言是否明确；是否方便验收 | 缺少测试覆盖；测试依赖未声明的环境；断言模糊；缺少关键日志；状态不可观测。**注意：本维度不检查"能否编译通过"，由阶段 7 负责** |

**评级与动作**：

| 综合评分 | 功能错误 | 动作 |
|---------|---------|------|
| ≥ 8.0 | 无 | 通过，输出审查报告，进入阶段 7 |
| ≥ 8.0 | 有 | 不通过，必须回到阶段 1/2 重新确认需求边界，或回到阶段 4 修复 |
| 5.0 - 7.9 | 无 | 有条件通过，列出阻塞问题（架构/质量违规）和建议项，优先修复阻塞问题后重新审查 |

```markdown
### 建议项（可选优化）
- [ ] <建议 1>

### 与设计文档的偏差
- plan.md 步骤 X 要求 <...>，实际代码 <...>，偏差原因：...
```

**关键规则**：
- **功能错误绝对阻塞**：任何导致业务逻辑与需求不符的问题，无论综合评分多高，都必须列为阻塞问题，综合评分必须降到有条件通过区间
- **阻塞问题必须具体**：给出文件路径、函数名、具体问题，禁止泛泛而谈
- **不要替代码做假设**：如果某段代码意图不清楚，标记为"意图不明，需确认"
- **审查错误必须追踪**：所有功能错误须在 workflow-state.md 的 `review.blockers` 中记录；修复后必须重新审查

**出口**：审查 ≥8.0、**无功能错误**，进入阶段 7。

**不通过路径**：审查未通过（评分 < 8.0 或有功能错误）时，必须修复后重新走阶段 4 → 5 → 6 → 7。禁止在功能错误未修复时进入阶段 7 编译验证。

## 旁路：纯咨询不走开发流程

如果判断为纯咨询（不动手改代码），按以下场景路由：

| 用户意图 | 路由目标 |
|---------|---------|
| 技术选型、架构评审、设计方案评估 | **→ [solution-validator]** |
| 分析日志/报错、排查问题根因、诊断异常 | **→ 诊断分析**（系统性地分析日志/堆栈/现象，输出根因假设与验证建议） |
| 代码结构分析、模块依赖梳理 | **→ [code-architecture-analyzer]** |
| Git 操作咨询、工作流建议 | **→ [git-tools]** |

**诊断分析旁路规则**：
- 用户说"帮我看看这个报错""分析一下日志""为什么崩溃了" → 属于诊断咨询
- 诊断咨询**不修改代码**，只输出分析结论和修复建议
- 如用户随后说"按建议修一下""帮我改" → **立即切换回开发任务流程**，走完整 SDD

纯咨询的出口不受 SDD 流程约束，但如用户随后说"那就按这个做"，立即切换回开发任务流程。

## 状态记录

每个开发任务应创建一个状态文件，防止上下文丢失后流程断裂：

```markdown
# workflow-state.md

task: "修复搜索分页 bug"
stage: "code-review"  # 当前阶段，可选值参考下方
confirmed:
  requirement: true   # 需求已确认
  compile_method: true  # 阶段 1 编译与运行验证方式已确认
  design: true        # 方案已确认（含 plan.md 中的编译与运行验证方案）
  execution: true     # 代码已执行
compiled:
  status: "passed"    # 阶段 7 结果：passed / skipped / failed / not-started
  command: "make"     # 实际使用的编译命令
  build_system: "make"  # 构建系统
  working_dir: "."    # 编译执行目录
  estimated_duration: "short"  # 预计构建时长：short / medium / long
  run_verification: true  # 是否需要运行验证
  skip_conditions: "环境缺失时经用户明确同意可跳过"  # 允许跳过编译的条件
  user_authorized: true  # 阶段 7 执行前是否再次获得用户授权
pre_review:
  passed: true        # 执行后预自检是否通过
review:
  score: 8.6          # 审查评分
  passed: true        # 是否通过
artifacts:
  requirement: "Agentic/sdd/<需求名称>/req-confirm.md"
  spec: "Agentic/sdd/<需求名称>/spec.md"
  plan: "Agentic/sdd/<需求名称>/plan.md"
  tasks: "Agentic/sdd/<需求名称>/tasks.md"
  test_strategy: "Agentic/sdd/<需求名称>/test-strategy.md"
  test_cases: "Agentic/sdd/<需求名称>/test-cases.md"
  review: "Agentic/sdd/<需求名称>/review-report.md"

# stage 可选值（与阶段编号对应）
# requirement-clarification, solution-design, user-confirmation,
# code-execution, post-execution-self-review, code-review,
# compilation-verification, acceptance-retrospective
```

状态文件及全部 SDD 产物统一放在项目目录的 `Agentic/sdd/<需求名称>/` 下，一个需求一个子目录，方便跨会话恢复进度。

## 禁止事项（红线）

以下行为在任何情况下都不允许：

1. **需求未确认就写 spec**
2. **方案未审核就执行代码**
3. **代码未审查就告诉用户"做完了"**
4. **擅自跳过 requirement-clarifier**（即使你觉得需求很清楚，至少输出一个简化的确认单让用户点头）
5. **执行时擅自改 plan**（发现 plan 有问题，停下来向用户说明，补充 plan 后再继续）
6. **审查给自己放水**（已知缺陷必须扣分，不能因为是自己写的代码就睁一只眼闭一只眼）
7. **功能错误降级为建议项以通过审查**（任何业务逻辑与需求不符的问题都是阻塞问题）
8. **在审查发现功能错误时，未经修复就进入复盘或结束流程**
9. **在收到阶段 3 有效确认前，以"用户可能想快点看到结果"为由提前执行代码**
10. **跳过执行前自检直接写代码**（tasks.md 的可行性、依赖闭环、文件清单对齐必须在动手前验证）
11. **跳过执行后预自检直接进入 code-review**（执行者必须先自检一遍，不能把明显错误推给审查环节）
12. **阶段 7 最终编译前未处理需单独请示的情形**：阶段 3 确认已覆盖常规编译授权，但在编译命令未确认、构建时间过长、用户此前跳过编译后重新编译、用户要求变更编译命令时，必须再次请示，不得擅自执行
13. **阶段 1 未确认编译方法就进入阶段 2 设计**：编译与运行验证方式必须在需求澄清阶段明确提出并由用户确认
14. **阶段 7 使用未经阶段 1/3 确认的编译命令**：未经用户确认的编译命令禁止执行，必须先回到阶段 1/2 补充确认
15. **禁止进入纯 plan 模式**：方案设计是执行的前提，禁止只输出 plan.md/tasks.md 而不继续推进，或在未获得"确认执行"类有效确认时长期停留在阶段 2
16. **禁止进入 ask 用户对话模式**：除阶段 3 等必要的用户确认检查点外，各阶段应直接输出结构化交付物（清单、表格、代码块），禁止使用 `AskUserQuestion` 开启多轮碎片化追问；待确认项须一次性结构化列出
17. **禁止用非结构化内容替代必要交付物**：阶段输出必须保持结构化，确保用户可快速确认并衔接后续流程

## 项目工程化工作流对接

当项目存在 `AIRunWorkDocs/project_wiki/overview.md` 或 `AIRunWorkDocs/red_lines/red_lines.yaml` 时，视为已启用 `engineering-workflow`。此时：

- **阶段 2（方案设计）**：由 `engineering-workflow` 生成/更新 `AIRunWorkDocs/runtime/TECH_SPEC.md` 与 `AIRunWorkDocs/runtime/subtasks.json`，替代通用 `spec-driven-agent` 的 spec/plan/tasks 模板。
- **阶段 4（代码执行）**：由 `engineering-workflow` 按 8 阶段流水线推进，提供项目地图、红线、脚本验证与跨会话记忆。
- **阶段 6（代码审查）**：审查者除对照通用规范外，还需检查 `AIRunWorkDocs/runtime/TECH_SPEC.md` §5 不变式与 `AIRunWorkDocs/red_lines/red_lines_critical.md`。
- **阶段 7（编译与运行验证）**：优先使用项目 `AIRunWorkDocs/tools/build_verify.sh`，以 sentinel 文件与退出码 0 为成功判据。

注意：`engineering-workflow` 替代 `spec-driven-agent` 在具体项目上的设计与执行角色，但不替代本 Skill 的总入口与质量门职责。语言相关细节由项目级 `agents/` 与 `semantic_bridge/` 承载。

## 与各个子 Skill 的关系

本 Skill 不替代子 Skill 的具体工作，而是：
- **做判断**：是否需要走流程？当前在哪个阶段？
- **做拦截**：防止跳步、防止未审核就执行
- **做路由**：明确当前阶段该调用哪个子 Skill 的方法论

子 Skill 负责各自领域的专业输出：
- requirement-clarifier：需求怎么澄清、确认单怎么写
- spec-driven-agent：spec/plan/tasks 怎么写、自评怎么打（已启用工程工作流的项目除外）
- engineering-workflow：项目工程化需求开发、项目地图、红线、跨会话记忆
- mermaid-diagrams：方案中的流程图/时序图/类图怎么画
- testing-strategy：测试方案与用例怎么设计
- code-review：代码怎么审、报告怎么出
- execution-retrospective：复盘怎么做、skill 怎么进化
- solution-validator：纯方案怎么评估
